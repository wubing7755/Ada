# SRS-to-Code Coverage Analysis

> Reference for `srs-review` skill — Pass K extension.
> Describes the workflow for comparing SRS requirements against actual source
> code implementation and producing structured gap analysis documents.

## When to Use

- After a significant code change that touched domain models or services
- Before a release to verify requirement coverage
- When asked "check the differences between code and SRS"
- When producing a traceability/coverage report

## Workflow

### 1. Extract REQs Programmatically First

For specs with 100+ requirements, use `execute_code` with a regex to extract
all `REQ-XXX | priority | Title` tuples into a checklist BEFORE reading any
source code. This prevents missing requirements during manual cross-reference.
The regex pattern should match the SRS's specific format:

```python
pattern = r'^(REQ-(?:F|NF)-\d+)\s+(🔴|🟡|🟢)\s+\[Actor:\s*(.*?)\]\n\nTitle\n(.*?)\n'
```

Store the output as your working checklist — you'll fill in status, files, and
remarks as you read each source file.

### 2. Read All Source Code, Then All Tests

Batch-read in dependency order: Domain models first → Services → Commands →
Interop → **Blazor components (.razor)** → **TypeScript/JS interop (ClientScripts/)**.
Then read all test files. For a ~45-file codebase (C# + TS + razor),
this takes ~15 batch `read_file` calls. Don't try to map REQs to files in your
head during reading — just absorb the full codebase, then cross-reference.

**MANDATORY: scan ALL source layers.** Reports generated by scanning only `.cs`
files systematically miss 10-20% of implementations hidden in:

- **TypeScript/JS interop** (`ClientScripts/index.ts`): drag previews, keyboard
  handling (Escape), click-vs-drag thresholds, drop indicators, window resize /
  visibility-change handlers
- **.razor component code-behind** (`@code` blocks): keyboard shortcut handlers
  (Ctrl+Tab, Ctrl+W, Ctrl+1-9), `OnAfterRenderAsync` lifecycle hooks for
  auto-restore, `OnInitialized` wiring
- **.razor markup**: declarative region/panel declarations, conditional
  rendering, event callbacks wired in Razor syntax

In Blazor WASM projects, a C#-only scan yields 58% coverage; a full scan including
TS + .razor yields 80%. The gap is the difference between an accurate report and an
embarrassing one.

### 3. Map Requirements to Code

For each requirement, ask three questions:
1. **Is the behavior implemented?** — find the method/property/component
2. **Is it tested?** — is there a test that exercises the AC?
3. **Is the integration wired?** — backend logic exists but UI may not call it

Use four status labels — the Tested/Implemented/Partial/Not Implemented system is preferred
because it distinguishes code-only from code+tests, which the simpler ✅/⚠️/❌/— system does not:

| Status | Meaning | Criteria |
|:---|:---|:---|
| **Tested** | 有代码 + 有测试 | Both implementation in `src/` AND test coverage in `tests/` exist |
| **Implemented** | 有代码，无测试 | Implementation exists but no test file covers this REQ |
| **Partial** | 部分实现 | Some behavior present but incomplete (e.g. domain model exists but UI wiring missing) |
| **Not Implemented** | 未实现 | No code exists for this requirement |

When a REQ spans both Domain/Services layer and UI/JS layer, classify based on the
*services layer* coverage — UI-only gaps get "Partial" if backend ready, "Not Implemented"
only if nothing exists at any layer. Document the UI gap in the Remarks column.

### 4. Separate Infrastructure from Feature Gaps

When reviewing requirements, distinguish two gap classes:

- **Infrastructure gaps**: Core design decisions made differently from SRS
  (e.g., JSON instead of XML, conditional ToolBar rendering). These belong in
  a separate "infrastructure deviation" document.
- **Feature gaps**: Individual requirements not yet implemented. These belong
  in a coverage matrix.

### 5. Produce Structured Output Documents

Three document types proven useful:

#### A) Coverage Matrix (`srs-coverage-matrix.md`)

Table per SRS section (§3.3, §3.4, …) with columns:
`编号 | 标题 | 状态 | 代码位置/说明`

End with statistics breakdown and a Top-N remaining gaps table.

#### B) Infrastructure Deviation Analysis (`srs-infra-deviation.md`)

Only for architecture-level mismatches (hierarchy, data model, serialization
format, event model). Do NOT include per-requirement feature gaps here.

Structure:
1. Overview table of architectural dimensions × consistency
2. Detailed deviation descriptions (linked SRS, current code, expected behavior, fix direction)
3. Data model side-by-side comparison
4. Event model comparison
5. Prioritized fix list

#### C) Base Class Optimization (`base-class-optimization.md`)

Code quality review of Domain/Services/Components classes against:
- SOLID principles
- Design patterns (State, Command, Strategy, Factory)
- Encapsulation (public setters, collection exposure)
- Thread safety
- Error handling consistency
- Testability and DI readiness
- SRS alignment gaps

Structure:
1. Overview table of optimization items × severity
2. Detailed item descriptions (code snippet, problem, fix)
3. Design pattern recommendations
4. SRS-alignment checklist
5. Priority-ordered action table

### 6. Iterate After Code Changes

When the user modifies code based on your analysis, re-read ALL changed files
(not just the ones you expect to change — users may touch adjacent files).
Then regenerate the coverage matrix and compare against the previous version.

Track which previous optimization items were addressed and which remain.

## Output Format Conventions

### Coverage Status Table (per-section)

```markdown
| REQ | 优先级 | 状态 | 实现文件 | 测试文件 | 备注 |
|-----|:------:|------|----------|----------|------|
| REQ-F-001 | 🔴 | **Tested** | `Domain/LayoutState.cs:143-154` | `Domain/LayoutStateTests.cs:9-18` | 9 个区域全部初始化 |
```

Each REQ gets one row. The Implementation and Test columns cite specific file
paths with line ranges. Use `—` when no test exists.

### Statistics Summary

Three views (all must be internally consistent — sums must equal total REQ count):

1. **Per-status**: Tested / Implemented / Partial / Not Implemented → count + percentage
2. **Per-priority**: P0/P1/P2 × status → 3×4 grid
3. **Per-section**: §3.3 through §4 → section × status

### Top-N Priority Gaps

```markdown
| # | REQ | 标题 | 优先级 | 影响 | 实施建议 |
|---|-----|------|:------:|------|---------|
```

### Appendices

- **A**: Test file inventory with test count per file and covered REQs
- **B**: Implementation file inventory with line counts and covered REQs

## Auditing an Existing Coverage Report

When asked to independently verify a generated coverage report's accuracy
(not generate a new one), use spot-check sampling rather than re-reading
the entire codebase:

### 1. Verify "Tested" Claims

Sample ~10 "Tested" REQs across different sections. For each, read the
test file at the claimed line range and verify:
- The test method actually exercises the REQ's acceptance criteria
- The test name / comment references the correct REQ or behavior
- The assertions match what the SRS specifies

### 2. Verify "Not Implemented" Claims

Sample ~8 "Not Implemented" REQs. For each, search the entire source tree
for keywords from the REQ description. A claim is **false** if you find an
implementation — mark it as misclassified.

**CRITICAL: scan ALL source layers, not just C#.** Reports generated by
scanning only `.cs` files systematically miss implementations in:
- **TypeScript/JS interop** (`ClientScripts/index.ts`): drag previews,
  keyboard handling (Escape), click-vs-drag thresholds, drop indicators
- **.razor component lifecycle** (`OnAfterRenderAsync`, `OnInitialized`):
  auto-restore layout, initialization hooks, event wiring
- **CSS**: visual feedback, animations, responsive behavior

In Blazor WASM projects, expect 10-20% of "Not Implemented" entries to\nbe false negatives from missed TS/razor layers. Always grep the full\nrepo, not just `src/Lib/**/*.cs`.\n\n**Specific patterns that evade C#-only scans:**\n- `HandleKeyDown` / `@onkeydown` in `.razor` files → keyboard shortcut REQs (F-116–118)\n- `OnAfterRenderAsync` with `firstRender` guard → auto-restore REQs (F-092)\n- `onWindowResize` / `onVisibilityChange` in `.ts` → edge-case REQs (F-129, F-137)\n- `@onkeydown` without `Ctrl` modifier → may indicate Esc handling too

### 3. Verify "Partial" Gap Descriptions

Sample ~5 "Partial" REQs. Check that the report's gap description
accurately identifies what's missing. Watch for:
- "Partial" that could be "Implemented" (all behavior exists, just
  goes through JS interop — which is the Blazor WASM architecture)
- "Partial" that should be "Not Implemented" (the claimed partial
  code doesn't actually do what the report says)

### 4. Spot Additional False Negatives

While verifying, watch for patterns in misclassified REQs. If one REQ
in a cluster (e.g., drag-related F-050–F-071) is misclassified due to
missed TS code, check adjacent REQs — they likely share the same blind spot.

### 5. Output Format

Produce an audit report with:
- Per-sample verification table (REQ, claim, actual, evidence)
- Misclassification count and accuracy rate per status category
- Root cause analysis (systematic bias, e.g., "only scanned C#")
- Corrected status recommendations with specific file/line evidence
- Estimated impact on overall report accuracy


## Pitfalls

- **Don't trust old traceability matrices.** The requirements-traceability.md
  file may be empty (0 bytes), stale (last updated before major refactors), or
  wrong (entries from a previous branch iteration). Always re-scan the codebase
  from scratch. If the old matrix exists, compare to produce a diff section at
  the end of the new report — but never use it as a starting assumption.

- **Extract REQs programmatically first.** For a 150+ REQ spec like Lib SRS,
  use `execute_code` with a regex to extract all `REQ-F-XXX | 🔴🟡🟢 | Title`
  tuples BEFORE reading any source code. This gives you a numbered checklist.
  Then batch-read all source files (Domain/, Services/, Commands/,
  Interop/), then all test files. Cross-reference manually — automation
  cannot distinguish "partial" from "tested" reliably.

- **Output columns**: per-section tables need 6 columns: REQ, Priority,
  Status, Implementation file(s), Test file(s), Remarks. The Implementation
  and Test columns MUST cite specific file paths (e.g.
  `Services/LayoutContext.cs:337-379`), not vague module names.

- **Statistics must be internally consistent.** Calculate three views:
  per-status (Tested/Implemented/Partial/Not Implemented), per-priority
  (P0/P1/P2 × status), and per-section. Verify: all 4 status counts sum to
  total REQ count; all 3 priority counts per status sum to total REQ count.

- **Separate infra from feature.** Infrastructure deviations (JSON vs XML,
  conditional ToolBar) are design decisions. Feature gaps (missing click
  handler) are implementation gaps. Mixing them creates confusion.

- **Use code location references.** Every status entry should cite a specific
  file path + method/line so the user can jump to it. Prefer `LayoutContext.cs`
  over "the open tab method".

- **The 35 "基建就绪" gap is real.** In Blazor component libraries, the
  largest gap class is often "backend implemented, component not wired."
  Highlight this explicitly — it's a different kind of work (UI plumbing vs.
  new logic) and the user should prioritize accordingly.

- **Don't count "基建就绪" as "已实现".** A DragService method that handles
  panel drops is NOT "implemented" if no component calls it. The — or Partial
  status exists precisely to track the backend-ready-to-UI gap.

- **Re-read after user changes.** Users may modify files you didn't list in
  your analysis. Always re-read the entire source tree, not just the files
  you mentioned.
