# 详细设计质量审计 (Detailed-Design Quality Audit)

## When to Use
- 用户要求"继续优化 / 审计 / 检查"详细设计文档的设计描述（SD-* 条目）
- 需要保证设计条目与 SRS 实现需求引用零漏零错、同类条目要素对称
- 提升设计描述的可验证性、边界覆盖与术语一致性

## Workflow

### Phase 0: 证据驱动读取
- 完整读取两份文档：SRS（重点是实现需求 REQ-F-268+，即带 Derivation 字段的块）与详细设计（全部 SD 条目）。不凭印象、不依赖历史结论。
- 提取实现需求集合（SRS 中带 `Derivation` 的 REQ-F 编号）与设计条目引用集合（【需求来源】字段）。

### Phase 1: 五维审计
1. **可验证性** — 每条描述能否推导测试判据。清除含糊词（"为依据之一"、"按需"、"等"），改写为具体状态谓词（如"撤销栈清空时清除未保存标记"、"仅包含当前配置存在的条目"）。
2. **输入/输出显式性** — 输入、输出、状态变化是否清楚；文件/解析/转换类条目用数据流转表（数据/来源/处理方式/输出目标）。
3. **边界与异常覆盖** — 空集合/空文件、首次进入（创建空会话）、操作取消、失败清理、目标文件已存在、无绑定文件时的待导入态。**失败清理必须同类对称**（如 SD-10/11 生成失败清理临时文件 → SD-5 保存失败也必须清理）。
4. **术语与一致性** — 模块主语统一（公共模块"资源工具"，子工具"线型生成工具/色表生成工具/…"）；章节标题名实相符（标题"线型资源生成"下不得放线宽生成）；无缩写漂移。
5. **HOW 深度与简洁平衡** — 无需求复述、无模板堆砌；简单条目简洁，复杂条目配流程图。

### Phase 2: 问题清单 + 完整改动文本 → 审阅
- 输出问题清单（按维度分类，含"SRS 层观察"单独列出——发现问题只报告、不擅自改 SRS）。
- 输出每条将改动的**完整条目文本（新旧对照）**到对话。
- 边界歧义（如"文件内容为空"算有效还是无效）给出明确选项（方案 A/B）让用户决策，**不擅自选**。
- **等待显式批准，批准前不改文档**。用户可能部分批准（如"修改 2 不用改"），按批准子集执行。

### Phase 3: 逐批执行 + 独立验证
- 批次顺序：术语/章节命名 → 实质性边界与可验证性修改。
- 每批后用 `scripts/verify_design_doc.py` 验证：SD 编号连续无重复、REQ 覆盖零漏零错（且不混入研发/用户层需求）、四字段完整、旧表述零残留、交叉引用可解析。

## Key Conventions（源自 目标项目，按项目泛化）
- 设计条目固定四字段【设计编号】【设计名称】【设计描述】【需求来源】，不得增加其他一级字段。
- 设计描述主语用需求域实体（资源工具 / 各子工具），禁内部组件名（如"索引分配组件"），禁"系统"式主语。
- 谓语 = 实现机制（编辑会话/修改命令/脏标记/撤销栈重做栈/临时文件/序列化），全文档统一。
- 自包含：禁引用兄弟功能条目（"处理流程与线型条目新增一致"）；跨条目机制引用可保留（"复用公共修改保护机制（SD-6）"）。
- 设计条目仅从 SRS 实现需求派生；研发/用户需求仅作语义依据。
- 同类条目（新增/删除/修改/索引分配/预览/校验/生成）要素骨架必须对称。

## 只读覆盖审查模式（需求覆盖审查，不改文档）

触发：用户以"软件设计评审人员"身份要求对 SRS 与设计条目做需求覆盖审查（覆盖审查/需求覆盖/八项检查），且明确"不修改任何文件、不生成新设计条目"。此时不走 Phase 2/3 改稿流程，只出报告。

### 六段式报告结构（严格按此输出，先脚本机械核对再人工语义核对）
1. **未覆盖需求**（需求编号+说明）
2. **部分覆盖需求**（需求编号+缺什么——设计描述未承载的需求语义）
3. **错误映射**（设计条目编号+来源编号+问题）
4. **重复设计**（设计条目编号对+说明）
5. **无需求依据的设计内容**（设计条目编号+内容+依据来源判断）
6. **建议修改的设计条目编号**（+理由）

外加八项检查逐项结论（每项 ✅/⚠️/❌+证据）：①每条需求至少被一条目覆盖（含间接覆盖判断）；②需求被完整覆盖（语义承载，非只填来源编号）；③是否只覆盖正常流程、遗漏重要异常；④是否遗漏接口/权限/安全/数据/状态要求；⑤无需求来源的设计条目；⑥来源填写错误（编号不存在/层级不符/内容不匹配）；⑦引用与其内容无关的需求；⑧需求被多条目重复设计。结论须带证据（引用需求原文/设计描述原文片段 + file:line）。

### 机械核对脚本化
1. 设计条目：按 `【设计编号】` split 设计文档，正则提取 SD-编号/名称/描述/`【需求来源】` 中的 F-\d+。
2. SRS 需求：按 ``` 代码块 split（每条 REQ 一块），正则取 REQ-F-NNN + Title + Description + Source。
3. 映射表：`#### SD-xx` 块取 `④需求来源：` 行。
4. 交叉核对：实现需求 ⊆ 条目来源（零未覆盖）；来源编号 ⊆ SRS 存在集合；来源层级合规（实现层 + 已批准例外）；每条需求恰好被一个条目引用（零重复设计）；设计文档来源集合 == 映射表来源集合（防映射表与设计文档漂移）。

### 语义覆盖核对要点（脚本查不出，必须人工）
- **间接覆盖链会丢语义**：研发需求→实现需求→SD 的链上，父需求的核心语义（尤其外部系统/接口）可能只存在于父需求文本。实测实例：F-113"工程文件用于'多进程 ARINC661 插件管理仿真工具'加载并使用"的语义在 SD-53 描述中完全缺失（SD-53 只写了持久化、恢复一致性、格式外部规格、未保存保护、图元库持久化）。核对方法：把每条研发/用户需求文本中提到的**外部系统**（目标项目 Server、插件管理仿真工具、甲方 .dll、集成格式规格）逐一 grep 设计文档，缺失即部分覆盖。仅核对实现子需求编号会漏报。
- **合并条目的触发场景词丢失**：F-414 原文"退出符号生成工具" vs SD-5 只写"退出资源工具"——合并条目丢原文场景词，判轻微部分覆盖。
- **同型组判重复**：数据一致性（F-270/F-291/F-315/F-416）、撤销重做（F-272/273 vs F-305/307）等同型组，逐对象核对对象名确实不同（资源表/色表 RGBA/工程文件/图元库），才按约定判"不算重复"。
- **例外来源要按约定背书**：研发层直接派生（F-062→SD-3）、性能直接成条（F-119~123→SD-57~61）、F-376 双用（SD-2+界面章节）等例外，报告中注明"按约定/决议"而非默认其合法。

## 横向一致性审查模式（只读，10 项标准）

触发：用户要求"对 SD-1~SD-N 做横向一致性审查（10 项标准）"，输出按问题类型和设计编号列出问题 + 统一建议、无问题项标注通过、附原文片段作证据，且"不修改文件、不重写条目"。与覆盖审查（编号↔需求语义）不同：本模式审查**文档内部横向一致性**——同一对象/同一机制/同一规则在不同条目间的表述是否统一、引用是否对齐、规则是否衔接。

### 前置读取（缺一不可，否则假阳性）
1. 完整读设计文档（全部 SD 条目四字段）。
2. 读映射表（逐条 ④需求来源 + ③设计范围 + ⑥与其他条目关系）。
3. **先读决议记录**（需求解析清单 1.4 决议 #1~25 与 5.11）——已确认的等价关系与命名约定就是判定基准，不读决议就判一致性必然误报（例：线型生成工具同时覆盖线宽是决议 #3 的既定事实，不是错误）。

### 已确认约定（判定"通过"，勿重复报）
- 可编辑文件 = 六类资源表配置表（决议 #14）；线型生成工具覆盖线型+线宽（#3）；符号标识即索引（#17）；索引断档≠缺失（#4）；默认索引 = 当前用户创建条目最大索引+1（#5）。
- 失败双模式并存不矛盾：前置校验失败=整体阻止（#16）；生成期单条目转换失败=标识并跳过该条目（F-304/F-412）。
- 命名约定：.c/.h 生成用"集成格式规格"（#8）；.dll 接口与工程文件格式用"外部提供的规格"（#9/#10）；索引唯一性检查实例化按工具命名（线型索引唯一性检查/颜色索引唯一性检查…）；同型对称条目按工具拆分不判重复；SD-6（配置撤销重做）与 SD-51（图形元素撤销重做）对象不同不判重复。

### 10 项检查与扫描要点
1. **业务对象命名** — 同对象多写法集中在同一工具内（实测：色表工具内"RGBA 数据"4 种写法：颜色分量配置/颜色分量数据/RGBA 数据/分量数据）。
2. **角色命名** — grep `操作员|设计人员|使用者`，仅"用户"则通过。
3. **模块/机制命名** — 简称漂移（"符号工具" vs 其余 20+ 处"符号生成工具"）；公共条目枚举子机制用简称 vs 子条目全名（SD-7 枚举校验规则用"虚线占空比检查"而条目名为"虚线占空比配置检查"）。
4. **状态表述** — 可编辑状态/有效配置/有效生成结果/有效符号外观语义分属不同对象时不算不一致。
5. **接口/外部系统命名** — 同型对称条目 3:3 分裂（"目标项目 Server 软件" vs "目标项目 Server"）；SRS 本身混用不豁免设计文档内部一致。
6. **相同处理规则** — 机制引用名 vs 条目名对齐（"默认索引分配机制"/"默认标识分配机制" vs SD-11"新增条目默认索引/标识分配"；"同名文件冲突处理机制" vs SD-9"生成结果保存冲突处理"）。
7. **同一异常同一处理** — 短语变体（"及相关原因" vs 其余 7 处"及可识别原因"）；失败/取消分支模式逐条目对照。
8. **处理顺序/依赖** — 规则悬挂：某条目引入对另一产物的规则而目标条目无衔接（SD-10"阻止工程文件生成" vs SD-53 通篇未提前置校验）。
9. **重复设计** — 同型组逐对象核对对象名确实不同才判"不算重复"；对称条目要素不对称（画布条目 SD-46/47/48"撤销与重做" vs SD-49/50 仅"撤销"；机制条目操作枚举漏类型，SD-51 漏"复制粘贴"）。
10. **需求来源编号** — 设计文档来源集合 == 映射表来源集合；每个 F-ID 存在于 SRS（含例外 F-062、F-119~123）；容量数值与 SRS Description 核对（目标项目 实例：100/100/100/500/50·20MB）。

### 机械流程与报告格式
1. Python 按 `【设计编号】` split 提取四字段；来源集合 set-equality 比对 + `re.search(re.escape(f)+r'\b', srs)` 存在性检查。
2. 术语变体扫描：每检查项一组 `re.finditer`，证据输出带上下文窗口（`desc[max(0,m.start()-20):m.end()+15]` 前后加省略号），一次 execute_code 跑多组。
3. 报告按检查项分组：每项 ✅ 通过 / ⚠️ 轻微 / ❌ 问题；问题含 设计编号+原文证据（带上下文省略号）+统一建议；⚠️ 轻微项单列不混入 ❌；结尾问题汇总表（#/类型/条目/问题/建议）；最后复盘四段：做了什么/发现/文件/遇到的问题。
4. 文件末尾条目易被 read_file 截断显示误判缺失（SD-61 的 F-123 显示到【需求来源】即止），用 `repr(tail)` 验证，勿凭显示断言缺编号。

## 最终交付检查模式（13 项规则，只读）

触发：用户要求对 SD-* 执行"最终交付检查 / 终检 / 13 项规则检查"，输出"可直接交付的条目 / 仍需修订的条目及原因 / 未解决的待确认项"，且"不修改文件、不重写条目"。与覆盖审查（编号↔需求语义）、横向一致性审查（文档内部横向一致）不同：本模式是**交付闸门终检**——13 项规则一次全查，按交付就绪度分级输出。

### 13 项规则速查
1. 只含四字段【设计编号/名称/描述/需求来源】；2. 编号唯一连续；3. 名称准确简洁（≤16 字、名实相符）；4. 描述为完整自然段（单段、句号结尾）；5. 无列表化/章节化/过度细分（合并同型需求不算过度细分）；6. 无仅重复需求原文（相似度筛查+设计决策注入判定）；7. 无编码级实现痕迹（.c/.h 生成产物名除外）；8. 无未覆盖需求（实现需求全覆盖）；9. 无无来源设计内容（关键细节须有决议/研发需求依据）；10. 无需求编号错误（存在性+层级合规）；11. 无重复/冲突/术语不一致（变体扫描）；12. 无"待确认/设计假设"残留；13. 无分析说明/辅助文字混入。

### 机械流程
1. SRS 块解析用 `r'```\n(REQ-F-\d+.*?)\n```'` 普通捕获（lookahead/`\s*` 变体 0 命中）；实现需求 = 块内含 `Derivation` 字段的 REQ-F。字段按块内独立行 Title/Description/Source/Derivation 切换收集器解析。
2. 设计条目按 `\n(?=【设计编号】)` split；【需求来源】捕获后剔除 `^#` 开头行防章节标题吸入（复用已有 pitfall 修复）。
3. 规则 8/10 集合比对：实现需求 ⊆ 条目来源（零未覆盖）；来源 ⊆ SRS 存在集合；来源层级 ⊆ 实现需求 ∪ 研发例外（F-062、F-119~123）。
4. 规则 6：`SequenceMatcher(None, '；'.join(来源需求desc), sd_desc).ratio()` >0.45 列候选人工判；判"通过"标准 = 注入设计决策（触发时机/阻止粒度/取消分支/修改历史/后续流程枚举/合并多条需求）。
5. 规则 11 变体扫描组（一次 execute_code 跑多组 re.finditer）：工具名简称、Server 表述（`目标项目 Server(?! 软件)`）、机制引用名、检查规则名 vs 条目名对齐、RGBA 称谓、撤销重做表述对称性（新增"回滚"/删除"恢复或回滚"/修改"可撤销与重做"）。
6. 规则 12/13 关键词表扫描（`待确认|待定|假设|暂定|TODO|TBD` / `注[:：]|说明[:：]|详见|参见|本条目|设计意图`）；规则 3/4/7 名称长度、句号结尾、编码痕迹正则。

### 报告三段式（用户约定，中文+证据）
① **可直接交付条目**（13 规则表逐项 ✅+证据）；② **仍需修订条目及原因**（阻塞项 vs 轻微观察项分开，轻微项不混入阻塞）；③ **未解决的待确认项**（预期非缺陷如未编写章节、机制引用衔接）。

### 判定要点
- 校验/导入类需求语义单一，相似度高是自然现象，**高相似 ≠ 仅重复需求原文**；判据是设计决策是否注入（实测 SD-28 sim=0.86 仍判通过）。
- 交付结论常为"全部可直接交付 + 轻微观察 + 预期待确认"，不要为凑问题报缺陷；决议记录仍是判定基准，机制引用衔接（如 SD-53 描述含 F-414/F-416 语义但来源仅 F-315）不算无来源。

## 交付级缺口评估（行为级 vs 实现级）

用户问\"开发者凭这份文档能否开发出可交付软件\"时，按缺口清单评估，结论分\"行为级合格 / 实现级不足\"两级——不要笼统说\"能\"或\"不能\"。实测缺口清单（按阻塞度排序）：

| 缺口 | 开发者会遇到什么 |
|---|---|
| 数据模型 | 条目/属性字段与类型未定义，无法建类与序列化 |
| 文件格式 | 可编辑文件/工程文件序列化格式未定义，无法实现打开/保存 |
| 生成格式 | .c/.h 输出规格空白，核心生成器无法实现（最大风险） |
| 外部接口依赖 | .dll 绘制接口、仿真工具工程格式、行业标准——无法在文档内自造，须显式声明为外部依赖 |
| UI 设计 | 图形界面无布局/控件/交互定义（补法见 ada-srs-to-detailed-design 的 5.7 模式） |
| 性能/容量 | 容量需求无实现需求支撑时无设计落地 |
| 测试验收 | 有判据无测试用例/验收标准 |

分类处置：**文档可补**（数据模型/文件格式/UI/性能/测试，但需需求层确认输入）｜**外部依赖需获取**（行业标准/甲方接口，先问用户手上有多少再定补深）｜**技术验证需做**（解码/栅格化/动态加载选型，spike 验证）。外部信息缺失时优先补文档可补项，不编造格式。

## 技术可行性审计（用户问"是否有可行性 / 内容描述是否准确"时）

与追溯审计（编号覆盖）不同：可行性审计评估**机制可实现性**与**描述语义准确性**，必须提取 SRS 实现需求 Description 原文逐条对照（非仅编号）。

1. **语义一致性对照**：逐条比对 SD 描述与需求原文——是否篡改需求语义、是否遗漏行为、是否设计自加延伸（如 SD-62"供资源生成使用"超出 REQ-F-112"绘制外观"）。自加延伸列入观察点请用户确认，不擅自删。
2. **机制可行性评估**：命令模式撤销、临时文件替换、会话保持、异步取消、图像/TTF 解析、DLL 加载均为成熟技术，行为级通常合格；逐机制确认无"需要发明新技术"的表述。
3. **阻塞性缺口识别**：未定义的格式/接口 = 阻塞项（目标项目 集成格式 → 生成器条目、DLL 导出接口 → SD-62、仿真工具工程格式 → SD-63、字体字符范围/尺寸 → SD-50、占空比有效范围 → SD-19）。分级：
   | 等级 | 判定 | 处置 |
   |---|---|---|
   | ✅ 现在可实现 | 机制成熟且无外部输入依赖 | 正常推进 |
   | ⚠️ 部分可行 | 逻辑骨架成立，判定常量悬空 | 规格化："作为生成输入提供" |
   | 🔴 阻塞 | 核心内容依赖未定义格式/接口 | 不编造，声明外部依赖 |
   **关键判断：可编辑文件格式是工具自定义的，不受外部约束**——SD-2~5、SD-63"对称格式"机制成立，数据模型可自由设计，不属阻塞。
4. **空头承诺识别**："保证可编译链接并按索引获取"但无格式定义可验证 → 无法兑现的承诺，须条件化（见 Pitfalls）。
5. **外部信息确认**：先问用户手上有什么（目标项目 标准、DLL 接口文档、工程格式定义）。确认缺失 → 不编造格式，先做无依赖部分，格式以"规格输入"留口。
6. **用户偏好（已验证）**：用户倾向**条目级修改**（优化/修改/扩展），否掉"新增章节/附录"方案。新增独立条目须有实现需求派生依据；91/91 全覆盖时无新增空间，除非用户指定需求来源。边界歧义给方案 A/B 让用户逐项决策（本类项目已定：索引断档不判缺失、DLL 进程内调用、可编辑文件内嵌解析数据——见 references 决策记录）。用户明确：详细文档修改**直接改文件**（V4A patch 落盘），不建复杂同步机制/转换管线，不做章节级结构改动。

### 5.7 界面承载复核

审计 5.7 界面设计时，逐条检查**需要界面承载的 SD 是否在 5.7 有对应元素**（增删按钮/属性编辑/预览/导入信息/失败提示/确认对话框/保存与打开入口），并核对关联条目列是否覆盖对应 SD。实测 4 类高频缺口：

| 缺口 | 实例 |
|---|---|
| 保存入口缺失 | SD-5 可编辑文件保存无 5.7 交互模式 → 补"保存可编辑文件"小节 |
| 工程文件操作区缺失 | SD-63/64 符号工程文件打开/保存/关闭无界面承载 → 界面表补行 |
| 确认对话框缺失 | SD-67 停用前影响范围确认无承载 → 图元库面板职责补"停用前影响范围确认提示" |
| 失败/状态标识缺失 | SD-50"转换失败条目在界面显著标识"无承载 → 条目列表区补"含转换失败条目显著标识" |

复核后必须：`grep -c "^#### 5.7.2.x "` 验证编号连续唯一（插入小节+顺延编号后极易重复）；核对新插入内容的交叉引用指向（见 Pitfalls）。

## Pitfalls

### search_files/rg 在中文路径下失败（Windows/MSYS）
绝对路径含 CJK 字符时 `search_files` 报 `rg: ... IO error ... 系统找不到指定的路径`（MSYS 路径转换问题，文件实际存在）。`read_file` 正常。批量校验改用 Python 脚本（execute_code / terminal python）以 `open(path, encoding='utf-8')` 读取。

### 【需求来源】正则吸进章节标题（集合比对假差异）
按 `【需求来源】\s*\n(.*?)(?=\n【设计编号】|\Z)` 提取来源字段时，每节最后一条的捕获会延伸到下一节 `## 5.x` 标题之后（下一个【设计编号】在标题之后），把标题行混入来源集合 → 与映射表的集合比对报假差异、SRS 存在性检查报假缺失。修复：捕获后剔除 `^#` 开头的行，或改用 `【设计编号】|^## ` 双边界。实测 61 条解析出 6 条假差异（SD-11/23/30/36/42/56）均为此因。

### 含糊词不可验证
"未保存判定以历史栈中是否存在未撤销修改为依据之一"无测试判据。改写为"撤销与重做操作执行后，会话重新计算未保存状态：配置恢复至与最近保存状态一致时清除未保存标记，否则保持已修改状态"。

### 失败清理不对称
生成失败清理（SD-10/11）存在时，保存失败（SD-5）、取消（SD-11）必须同样清理临时文件——逐条检查兄弟条目对称性。

### 绝对化表述与既有机制冲突
"保证不存在未保存修改丢失"与"用户可选择放弃"的三选一保护机制矛盾——应改为"按公共修改保护机制处理，避免被静默丢弃"。

### 逐段 grep 提取实现需求混入 Source 父需求编号
按章节行范围 `grep REQ-F-` 提取实现需求会误收条目 Source 字段里的父需求编号（研发需求层，如 REQ-F-060~113），产生假的"未覆盖"清单。识别条目 ID 的正确模式：行首 `REQ-F-NNN` 且其后数行出现 `Title`（SRS 条目为 ``` 代码块：REQ-F-NNN / Title / Description / Source / Derivation）。提取后必须双向校验：SD 引用 ⊆ 实现需求（不混入上层），实现需求 ⊆ SD 引用（零漏设计）。配方

### 需求层级不可按编号区间猜（脚本分类会误判 F-153/154）
解析清单 1.1 写"研发=REQ-F-060~123"，但该区间只是约数：符号工具研发需求 F-153/F-154 编号 >123 仍属研发层。按 `60<=num<=123 → 研发` 的脚本分类会把 F-153/154 误判为实现层，产生假"未覆盖需求"报告。层级 ground truth = ①SRS 条目是否带 `Derivation` 字段（实现需求必带，研发/用户不带）；②需求解析清单的章节结构（`#### 2.7.1 研发需求（7 条）` 列出 F-109~113/153/154）。脚本分类结果必须与解析清单章节标题交叉验证；出现"未覆盖"先查是否层级误判，再查是否真缺条目。

### SRS 编号断层不是追溯缺失
REQ-F 编号可以不连续（如 318–375 整体不存在于 SRS）。发现 SD 未引用某区间编号时，先确认该编号是否真实存在于 SRS 条目列表；源文档断层 ≠ 漏设计，不得据此报缺陷。

### 设计描述写死可配置枚举
描述中列出具体格式名/类型名（如 .JPG/.PNG/.BMP/.TIF/.HEIF）违反"设计描述不写死可配置枚举"约定。审计时对照 REQ 原文：需求若以"等"开放表述，设计侧应同样通配，设计不得比需求更具体。列为观察点让用户确认，不擅自改写。

### 跨模块组件表关联条目标注
模块开头的组件表把其他模块的 SD 条目关联到本模块组件（如公共模块"编辑会话"关联色表模块的 SD-34）时，语义上可能成立（该组件承载对应数据结构），但也可能是笔误。审计时列入观察点请用户确认，不擅自移动条目。

### 空头承诺条件化
设计描述中"保证可编译链接""保证按索引获取"等承诺在格式未定义时无法兑现（空头承诺）。统一改写为条件式："生成内容按 目标项目 Server 集成格式**规格**组织条目数据与索引声明，**使**生成结果可编译链接并按索引获取××数据；集成格式规格**作为生成输入提供**，生成器按其组织输出"。禁"保证"式事实陈述；验收判据用"使…满足"，机制描述用"规格作为输入"。

### 约束与描述术语必须同步
改【设计描述】时，同条目【设计要求及约束】中可能残留同义旧表述（如"按字体资源要求"vs 新描述"按字体资源规格要求"）。验证脚本 old_term 检查必须覆盖两者——残留定位用 `grep -n "旧表述" 设计文档` 查全部出现行（含约束行），逐处替换后再跑 verify 收尾。

### 索引断档 ≠ 缺失
用户删除资源条目会自然导致索引不连续，属正常状态。设计"索引缺失"判定时区分：缺失 = 条目未设置有效索引值；断档不作缺失判定、不产生问题条目。边界歧义给方案 A/B 让用户决策（本类项目已定：断档不判缺失）。

### native DLL 崩溃边界诚实化
C/C++ DLL 访问违例无法被托管异常捕获，直接终止进程。"异常保护"表述必须诚实区分：进程内调用时明确"加载失败/接口缺失/调用返回失败可检测；进程级访问违例不可捕获，不在本条目保证范围内"；若要真隔离须子进程承载。审计时必查此类准确性瑕疵。

### V4A patch 插入+重编号会复制块
插入新编号小节并顺延后续编号时，若替换块里包含本应移动/保留的上下文，会产生重复块（实测：插入 5.7.2.2 保存后原 5.7.2.2 未保存提示重复出现两次）。patch 后必须验证编号唯一性：`grep -c "^#### 5.7.2.2 " 文档` 应为 1；V4A 多 hunk 一次提交后逐个 grep 受影响编号。

### 新增交叉引用后核对指向
新插入条目的机制引用必须与目标匹配：失败反馈是章节 5.7.2.6 而非 SD-6（未保存修改提示）；补全失败反馈的 SD 列表（保存失败对应 SD-5，此前缺失）。引用错误靠 patch diff 逐行审阅发现，勿只信 patch 成功返回。

### 同步 .docx 前先核实是否同一文档
同目录 .docx 可能是甲方另一份文档而非 md 的 Word 交付版，勿默认同步。核实方法：文档标题、SD-1 条目内容、需求编号风格（SR-xxx vs REQ-F-xxx）、是否含嵌入对象（EMF/ole）。确认无关后不做同步，避免建立无用转换管线（用户偏好直接改源文件）。
