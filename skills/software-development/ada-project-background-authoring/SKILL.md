# 项目背景 Authoring（SRS 前置阶段）

项目背景文档是 SRS 的输入材料：把原始需求/口头描述整理成结构化背景，通过逐轮确认把"待确认"变成"已确认"，最后输出一份可直接交给 SRS 阶段的文档。典型项目流程：**背景 → SRS → 详细设计 → 工程 → 开发 → 测试部署**。

## When to Use

- 用户说"梳理项目背景"、"项目背景"、"整理原始需求"（阶段一）
- 用户给了原始需求描述，要求整理成适合后续写 SRS 的背景文档
- 任何"先确认信息再写需求"的启动阶段

## 用户核心工作流约定（本用户必须遵守）

1. **完整草案先输出到对话审阅，批准前不写文件、不改文档**。即使用户在提示词里写"如果具备文件写入能力则写入 docs/xxx.md"，也先输出全文，最后请求批准。
2. **未知信息统一标记"待确认"；合理推断标记"设计假设"；不得把推断写成已确认需求**。
3. **不虚构个人信息**（工作经历、技术成果、荣誉）。动机性描述（"建设背景""现有问题"）要注明"并非已确认事实"。
4. **待确认事项逐轮与用户确认**：输出待确认清单 → 用户逐项回答 → 把答案折叠进文档 → 每轮输出受影响章节的最终文本（不必重复未改动章节）→ 最终批准后落盘。
5. **对歧义答案显式声明解读**让用户校验，不要猜错继续走。例："第 10 条我理解为联系表单（承接上轮讨论）：静态部署下无法干净实现则废弃"。编号顺序错位时整理成"我理解的对照表"。
6. 文档收尾用**"已确认事项汇总"表**（事项/结论），作为 SRS 的直接输入。

## 13 节标准结构

1. **项目基本信息**：名称未定用"项目名称：待定 + 项目代号：XXX"，不得虚构正式名称；含类型/性质/部署平台/技术方向/当前状态/建设方式
2. **项目现状**：旧项目状态、从零建设、不兼容旧代码
3. **建设背景**：建设动机列表（集中展示、沉淀博客、招聘入口、长期主页等）
4. **现有问题**：无统一个人网站的典型问题——**作为建设动机，非已确认事实**
5. **建设目标**：总体 / 展示 / 技术 / 长期（长期目标≠首期范围，明确标注）
6. **目标访问者**：招聘人员/技术同行/潜在合作伙伴/普通访问者/网站维护者（默认=所有者）；确认是否设优先级
7. **网站内容范围**：只列内容板块，不展开功能需求
8. **技术背景**：选型理由 + 约束成对写（如 Blazor WASM / GitHub Pages / GitHub Actions）
9. **项目边界**：初步包含 / 初步不包含 / 待确认范围（三项）
10. **主要约束**：静态部署、无密钥、路由、加载成本、占位符、少依赖等
11. **项目成功标准**：背景层面表述，明确"可测试验收标准在 SRS 中定义"
12. **设计假设**：全部标注为推断，逐条可被用户推翻
13. **待确认事项**：覆盖名称/账号/定位/访问者/页面/数据来源/多语言/简历/照片/隐私范围/风格/域名/SEO/统计；确认完毕后转为"已确认事项汇总"表

## 静态站点类项目的常见待确认项与决策框架

当项目是 GitHub Pages / 静态托管时，关键技术决策见 `ada-github-pages-static-site`。常见需与用户确认的架构点：

- 内容源（博客等）的存放方式：**方案 A**（源进仓库，构建期转换，发布产物不含源，CI 全自动）vs **方案 B**（源仅本地，不进仓库 → Actions 拿不到源，CI 中断）。"不进发布产物"与"不进仓库"含义完全不同，必须向用户问清
- 网页端能否"上传内容"：静态站不能直接写（无服务端 + 客户端不能持凭据）；可行路径 Git 工作流 / Issues 中转 / 第三方 CMS
- 联系表单在无后端下的取舍：第三方表单服务（外部依赖）vs 邮件链接降级 vs 废弃
- GitHub API：仅公开只读接口，匿名限流 ~60 次/小时/IP，数据量大需构建期预取或静态兜底

## Output 要求

- 简体中文、Markdown、正式客观、无宣传文案
- 阶段内不输出：功能需求、页面原型、数据模型、详细技术方案、代码、SRS
- 结果应能直接作为后续 SRS 的输入材料

## Verification Checklist

- [ ] 未知信息全部标"待确认"、推断全部标"设计假设"
- [ ] 无虚构个人信息；动机性描述有"非已确认事实"声明
- [ ] 待确认事项已逐轮确认并折叠进文档，最后有"已确认事项汇总"表
- [ ] 文件未在批准前写入；批准后落盘并读回验证
- [ ] 未输出 SRS/设计/代码内容
