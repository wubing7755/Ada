# 设计条目多轮审查清单（SRS → 详细设计交付）

覆盖五轮审查：格式规范 / 需求覆盖 / 可理解性 / 横向一致性 / 最终交付检查。每轮独立输出"问题+原因+修改建议"（附原文证据），不直接重写；用户批准后才修。语义审查一律 delegate_task 独立子代理 + 自己跑脚本机械核对交叉验证；子代理 context 必须写明"已确认决议/不判为错误的等价关系"，否则会把确认过的决议当错误报。

## 轮 1 格式规范（详见 SKILL.md「格式规范审查」节）

- 四字段齐全/顺序/无增删；描述单一自然段（无空行分段/列表/编号/标题）；编号唯一连续；来源逐行 `^F-\d+$`；长度 >330 字提示；无编码级标记。
- 条目标题行（### SD-N）与字段重复、文档标题行——用户格式严格时删除，保留模块标题（## 5.x）。
- 脚本解析：按 `^### SD-N` 分割条目块；标签提取 `【([^】]+)】` 后与去括号基准比较；来源行过滤模块标题并入。
- EOL：patch 工具可能插入 LF 到 CRLF 文件 → 批量修改后统一行尾（`text.replace('\r\n','\n').replace('\n','\r\n')`）。

## 轮 2 需求覆盖（详见 SKILL.md「覆盖审查」节）

- 机械：实现需求全覆盖 / 无来源条目 / 来源合法性（实现需求+已批准研发直接派生白名单）/ 需求被多条目引用为空。
- 语义（子代理）：需求是否真正承载（非只填编号）；异常/失败/无效覆盖；接口/权限/安全/数据/状态遗漏；来源与描述错配；条目间重复。
- 典型缺口：外部系统交互语义缺失（符号工程文件漏"供插件管理仿真工具加载使用"）；触发场景缩水。
- SRS 层张力：识别后提交用户裁决，裁决后修订描述 + 登记决议记录。

## 轮 3 可理解性（开发人员视角，10 项）

1 功能清楚 2 处理过程清楚 3 关键判断/业务规则 4 输入输出 5 异常/失败 6 比需求具体（非复述） 7 无模糊表述 8 无编码级 9 无需求外业务 10 单一连贯自然段。

机械扫描与高频发现：
- **模糊词扫描**：`系统进行处理 / 根据情况 / 完成相关操作 / 统一管理 / 界面基础 / 正常工作 / 相关原因 / 可识别的默认 / 有效性识别 / 途径` 等；命中后甄别"空洞收尾句"（如"执行状态与结果有效性由本机制统一管理"）→ 删除或具体化为可执行规则（"仅当完整成功执行后，产出文件才标记为有效结果进入保存流程"）。
- **复述检测**：描述与需求 Description 连续 ≥25 字重合 = 整句复述；语义复述（如 RGBA 一致性条目）需补可执行约束（"保存与重新打开时按索引值持久化并重建映射"），否则增量不足。
- **术语消歧**：同一概念叠词（"线段定义"vs"虚线定义"——甲方 API 的"线段定义"实为线段）→ 统一改"线段"、注明"仅含 1 个线段即实线"。
- **默认配置构成对称性**：同族新增条目须说明默认配置构成（默认索引+对应属性）；字体（默认不关联 TTF）与符号（空图形元素集合）条目易漏，漏了开发者无法实现。
- **容量条目**："正常工作"须补判据（"在该容量规模下功能可用、不因容量而失败或丢失数据；除容量规模外无额外性能指标要求"）；容量口径要明确约束对象（"单个字体文件按不超过 20MB 评估"）。
- **失败模式对齐**：前置校验失败=整体阻止（决议）vs 生成期单条目转换失败=标识并跳过——两种模式的描述措辞不得混用（"阻止使用该条目生成"字面读作仅跳过）。

## 轮 4 横向一致性（10 项）

1 业务对象不同名 2 角色不同称呼 3 模块不同名 4 状态不同写法 5 接口/外部系统不同名 6 同规则矛盾 7 同异常不同处理 8 顺序/依赖冲突 9 重复设计 10 来源编号一致。

机械扫描与高频发现：
- **术语盘点**：全文对同一对象做变体统计。实测：RGBA 数据 4 种写法（颜色分量配置/颜色分量数据/RGBA 数据/RGBA 分量数据）；"符号工具"vs"符号生成工具"（简称混用）；"目标项目 Server"vs"目标项目 Server 软件"（3:3 分裂）。
- **机制引用名 vs 条目名**：生成条目引用"生成执行与结果管理机制""同名文件冲突处理机制"，与条目名"资源生成执行与结果管理""生成结果保存冲突处理"不对齐 → 引用名与条目名统一。
- **枚举用简称**：公共条目枚举校验规则用简称（"线宽配置检查""RGBA 数据检查"）而各校验条目为全名（"线宽配置有效性检查"）→ 用条目全名。
- **异常表述变体**："及相关原因"（沿需求原文）vs"及可识别原因"（其余 7 处）→ 统一。
- **规则悬挂**：公共机制条目引入的规则必须在对应功能条目有落点（实测 SD-10"阻止工程文件生成"规则在 SD-53 无前置校验表述）→ 补落点或删句。
- **对称条目要素不对称**：撤销/重做提及——新增/删除条目只写"撤销机制"、修改条目写"撤销与重做"、SD-51 枚举缺"复制粘贴" → 同型统一"撤销与重做"，机制条目枚举补全。
- **来源编号**：与映射表逐条一致；研发直接派生例外（F-062/F-119~123）合规；映射表/解析清单残留旧术语须与设计文件同步。

## 轮 5 最终交付检查（13 项）

四字段 / 编号唯一 / 名称准确简洁 / 描述单一自然段 / 无列表化·章节化·过度细分 / 不复述需求原文 / 无编码级 / 无未覆盖需求 / 无无来源设计内容 / 无需求编号错误 / 无重复·冲突·术语不一致 / 无"待确认"·"设计假设"残留 / 无分析说明·辅助文字混入。

执行要点：
- 机械：结构脚本（四字段/编号/自然段/术语残留/来源集合）+ "待确认/设计假设/TODO/TBD" 零命中扫描 + 文件仅含模块标题与条目正文（无前言/说明/表格外文字——描述与名称行是合法正文，不算辅助文字）。
- 语义（子代理）：名称名实相符、不复述需求（高相似条目须已注入设计决策）、无编码级、术语一致性。
- 结论三栏：可直接交付条目 / 仍需修订条目及原因 / 未解决的待确认项。
- 轻微项（如对称条目词序"回滚或恢复"vs"恢复或回滚"）可标注"可选统一、不阻塞交付"，由用户决定是否执行。

## 终检后执行项（用户确认后）

- 未解决待确认项落实：如 5.8 界面设计章节编写（结构见 SKILL.md「UI 界面设计覆盖」）、SD-53 需求来源按追溯需求补充 F-414/F-416——注意这会令同一需求被多条目引用（若此前"一需求一条目"是验证基线，需同步更新映射表并调整覆盖预期）。
- 修订后同步支持文档（映射表/解析清单），并登记决议编号（如 决议#26）。

## 输出形态与修订节奏

- 审查输出：通过项表格 + 按问题类型/设计编号列问题（原文片段证据 + 原因 + 修改方向）；无问题条目不列；不重写。
- 用户批准后修订：确定性修改（术语统一/表述对齐）直接做；需语义判断的（如 SD-20 术语消歧、默认配置构成）按建议方向改；改后跑轮 1 格式复查 + 术语残留扫描 + 来源集合不变性比对。
