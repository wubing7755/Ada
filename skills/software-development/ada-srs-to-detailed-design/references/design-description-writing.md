# 设计描述编写 — 完整示例与方法（SD-20 实例）

来源：多进程目标项目Server设计工具项目（2026-08 会话）。该项目详细设计条目采用 SD-N 编号 + 四字段格式（【设计编号】【设计名称】【设计描述】【需求来源】），权威规格在项目目录的 `软件详细设计报告-生成任务-提示词.md`（该文件是生成详细设计章节的任务提示，含全部编写约束，可作范本）。

## 四字段固定格式（只允许 4 个一级字段）

```txt
5.x.x.1 设计要求及约束    <- 概括需求行为/格式/规则，不复制原文
5.x.x.2 设计
【设计编号】SD-N
【设计名称】<核心职责，避免空泛>
【设计描述】<HOW>
【需求来源】REQ-F-XXX（只填实现需求编号，多条逐行）
```

禁止增加其他一级字段（【输入】【输出】【处理流程】【接口设计】【异常处理】等），相关内容自然写入【设计描述】。

## 核心检验标准

设计描述回答 HOW，不回答 WHAT。**可检验对照**：把设计描述删掉后，若实现者从需求原文+设计要求及约束仍知道怎么编码 → 描述只是复述需求，不合格。

## SD-20 终版（线宽条目新增，来源 REQ-F-380）

> 用户新增线宽条目时，线型生成工具创建线宽条目对象，通过默认索引分配机制（SD-23）分配当前未被占用的默认索引值，并设置默认线宽配置，使新条目具备可识别的初始内容。条目以修改命令形式加入编辑会话，触发会话脏标记，并刷新条目列表显示，新条目进入可编辑状态供用户修改。新增操作可经撤销机制回滚。

逐句职责表：

| 句段 | 设计职责 |
|---|---|
| 用户新增线宽条目时，线型生成工具创建线宽条目对象 | 触发 + 需求域主语（子工具）+ 首个动作 |
| 通过默认索引分配机制（SD-23）分配当前未被占用的默认索引值 | 核心步骤 + 子机制协作引用（带编号） |
| 设置默认线宽配置，使新条目具备可识别的初始内容 | 默认值初始化（回应需求"可识别的默认配置"） |
| 条目以修改命令形式加入编辑会话，触发会话脏标记 | 命令封装 + 会话状态变化（脏标记是未保存提示工作的前提） |
| 并刷新条目列表显示 | 显示刷新（机制保留，组件名已去除） |
| 新条目进入可编辑状态供用户修改 | 结果状态 |
| 新增操作可经撤销机制回滚 | 边界/恢复（与公共撤销机制交互） |

对比父需求 REQ-F-380（"应创建该条目并显示在条目列表中，新条目应处于可编辑状态并具备可识别的默认配置"）：设计描述未复述需求，补充了需求没说的信息——怎么做（对象→索引→命令→会话→刷新）、牵连什么（脏标记、撤销机制、SD-23 协作）。

## 本版相对早期版本的演变（用户五次纠正的沉淀）

1. **去掉"X 由 Y 组件实现"总起句**（用户："这句话我感觉没有必要，直接介绍管理组件的功能不是更好吗"）。理由：独立总起句零信息——归属已从章节位置 + 模块组件表两处可得；删除后首句腾出位置承载触发 + 首个动作。
2. **禁止引用兄弟功能条目流程**（用户："整体处理流程与线型条目新增（SD-14）一致，这句话不妥当，难道开发者还要再看SD-14设计条目"）。早期版本曾把"复用声明（带编号）"当优点，被否：对称功能条目（线型/线宽/色表/图像/字体/符号的增删改）各自写全流程，自包含优先于去重——被引条目变更会让"一致"静默失效。
3. **引用边界**：只允许引用"公共机制词汇"（编辑会话、命令机制）和"子机制条目"（SD-23 默认索引分配，读者不看也能理解主流程）；禁止引用"对称功能条目"（SD-14）。
4. **彻底不出现内部组件名**（用户："可以直接不出现这个内部设计的组件吗"）。组件名是职责标签、不携带实现信息，且出现即引发"是否要描述组件"的额外负担；归属由章节位置 + 模块组件表承载，无需在每条描述里重复。删除组件名，保留实现机制（编辑会话、修改命令、脏标记、撤销栈）与跨条目机制引用。
5. **主语 = 需求域实体（子工具 / 资源工具）**（用户："主语变为5个具体的子工具是否可行呢"）。子工具是 SRS 概念、文档组织单位（5.2 目标项目 线型生成工具就是章节），读者不会期待额外"描述子工具"章节；同时避免无主句和"系统式"空泛描述。主语映射：公共模块=资源工具，各工具=线型/色表/图像/字体/符号生成工具。
6. **组织方向：需求驱动，不以组件为模块**（用户："我们的方向是从 SRS 中的'实现需求'派生设计条目，不要以组件为模块"）。曾探索按组件分章方案（组件表一行=一个章节），被明确否决；组件表降级为模块职责总览，与设计描述解耦。组件协作概述不设独立章节。

## 合格 / 不合格对照（同一需求 REQ-F-380）

不合格（需求复述，零设计信息）：

> 线宽条目新增功能支持用户新增线宽配置条目，创建条目并显示在列表中，新条目处于可编辑状态并具备默认配置。

不合格（外包给兄弟条目 + 出现组件名）：

> 线宽条目新增由线型工具条目管理组件实现，处理流程与线型条目新增（SD-14）一致。……

不合格（仅出现内部组件名）：

> 用户新增线宽条目时，线型工具条目管理组件创建线宽条目对象……（组件名是负担源，主语应为需求域实体"线型生成工具"）

合格（SD-20 终版）：删掉后实现者会丢失"用命令机制、走编辑会话、脏标记、关联 SD-23、可撤销"这些实现约束。

## 深度判断

- 简单条目：一段话即可（SD-20 属于此类，不堆模板）
- 中等/复杂条目（多步骤、数据流转、文件处理、多模块协作）：多段 + Mermaid 图（flowchart/sequenceDiagram 优先；节点少、黑白可读）或数据流转表（数据/来源/处理方式/输出目标）
- 不要求每条目覆盖输入/输出/接口/状态/异常全部方面，按实际复杂度选取

## 编写时的具体注意点

- 组件名称统一用文档第 5 章组件表名称，不新造（模块职责表先行）
- 引用子机制条目必须带编号（SD-xx），满足一致性检查；引用公共组件词汇无需编号
- 行为型条目（新增/删除/修改/生成/导入）：主语用子工具/资源工具（需求域实体），首句给触发或核心动作；内部组件名不出现
- 保留实现机制词（编辑会话、修改命令、脏标记、撤销栈、临时文件）——去掉的是组件名，不是机制；跨条目机制引用带编号（SD-xx）
- 性质保证型条目（数据一致性/有效性检查）："由 xxx 保证"或机制描述开头，不硬套组件归属
- 纯复用型条目：无新实现时写"复用 SD-x 机制"，不写"由新组件实现"以免误导
- SRS 无定量指标时不得编造响应时间/容量/超时/重试次数（性能类需求常留在研发层无实现子需求 → 覆盖风险提示）
- 不得擅自确定编程语言/框架/数据库/第三方库/文件字段定义，用技术中立表达
