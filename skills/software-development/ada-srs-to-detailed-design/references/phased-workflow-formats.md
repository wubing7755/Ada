# SRS → 详细设计 分阶段交付格式（实战模板）

目标项目 多进程设计工具项目验证过的各阶段交付格式。每阶段用户确认后才进入下一阶段。

## 1. 需求解析清单（14 字段/条）

每条需求按编号逐项整理，公共语境开头统一声明一次（角色、外部系统、触发方式、设计条目判定默认值），条目内不重复：

1. 需求编号；2. 需求名称；3. 需求主要内容；4. 需求涉及的用户、角色或外部系统；5. 功能触发条件；6. 主要输入；7. 主要处理过程；8. 主要输出；9. 关键业务规则；10. 涉及的数据或状态变化；11. 与其他模块或外部系统的交互；12. 主要异常或失败情况；13. 与其他需求的关联关系；14. 是否需要形成软件设计条目。

要求：保留原始编号；不改原意；不补无法确认的规则；无法确定标"待确认"；相似/重复需求指出关系不删除；本阶段不生成正式条目。

## 2. 待确认问题清单（收敛过滤）

只列确实影响设计条目编写、需业务/技术人员确认的问题：
- 按需求编号分类，每项说明影响的设计内容；
- 不过细技术问题（类、方法、数据库字段、框架选择）；
- 不影响当前设计编写的不列为阻塞；
- 不自行给出未经确认的业务结论。

用户给出决议后记入"决议记录"表（# + 事项 + 决议），设计条目/映射引用决议编号。已决议事项不再列为待确认。

## 3. 需求—设计条目映射表（7 字段/条目）

每条目：拟定设计编号 / 拟定设计名称 / 设计范围 / 对应需求编号 / 拆分或合并理由 / 与其他设计条目的关系 / 是否存在待确认内容。

后附覆盖分析五节：
- 未覆盖需求（实现需求必须全覆盖；研发/用户按约定间接覆盖，例外显式登记）；
- 重复覆盖但可能需要合并的条目；
- 范围过大的条目；
- 范围过小的条目；
- 仍需确认的问题。

用户可能拍板"多条需求对应一条设计"（合并授权）与"研发需求直接派生"（如 F-062 新建、F-119~123 性能分别编写）。

## 4. 正式设计条目（四字段）

```
【设计编号】SD-N（连续唯一）
【设计名称】…
【设计描述】单一自然段，按处理顺序；含触发/前置、输入与校验、处理、业务规则、数据状态、交互、输出、异常
【需求来源】F-XXX（多条逐行列出）
```

任务规格可能明确"只输出四字段、无'设计要求及约束'小节"——以任务提示为准。

## 5. 格式审查问题清单结构

按检查项给出结论 + 按设计编号列出问题与修改建议：术语命名一致性、对称条目表述一致性、描述长度（>300 字偏长）、标题行去留（严格四字段时删条目标题行、保留模块标题）、编号连续、来源格式、编码级内容。

## 6. 覆盖审查输出结构

- 未覆盖需求 / 部分覆盖需求 / 错误映射 / 重复设计 / 无需求依据的设计内容 / 建议修改的设计条目编号；
- 八项检查逐项结论：每条需求至少一条目覆盖（含间接）；语义承载（非只填编号）；异常覆盖；接口/权限/安全/数据/状态遗漏；无来源条目；来源填写错误；引用无关需求；重复设计。
