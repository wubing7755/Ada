# SRS → 详细设计 (SDD) 章节生成

## 触发条件

- 用户要求从分层 SRS（用户需求/研发需求/实现需求）生成《软件详细设计》的"详细设计"章节
- 军工 GJB 438B 风格文档链：技术协议 → SRS → 详细设计/HLD
- 输出文件通常命名为 `*-软件详细设计.md`，内容从 "5 详细设计" 开始
-

## 核心派生规则

1. **完整阅读 SRS 全三层**：用户需求、研发需求、实现需求都要读；上层需求仅作设计语境、语义解释和一致性检查，不直接派生条目。
2. **只有实现需求派生设计条目**：设计条目的【需求来源】只填实现需求编号。用户/研发需求编号混入 = 违规（用户显式决议性能/容量研发需求直接派生时除外——见规则 3）。编号必须来自实际 SRS，不照抄任务提示里的示例编号（示例 REQ-I-194 ≠ 实际文档的 REQ-F-XXX）。
3. **无实现子需求的研发/用户需求 → 覆盖风险**：不自行补条目、不直接作来源，内部标记即可。典型：性能/容量类需求常留在研发层（如 REQ-F-119~123），输出时作为覆盖风险提示。**例外：用户可显式决定性能/容量类研发需求直接派生设计条目**（实例：目标项目 F-119~123 分别编写 5 条，【需求来源】=研发需求编号）；以用户决议为准并在映射表注明。
4. **按模块组织，不按需求编号顺序**：先按业务职责划分模块/子模块（高内聚低耦合、数据归属明确），再在模块下安排条目。
5. **合理拆分 / 合并 / 公共提取**：
   - 一条实现需求可拆多条：独立职责、独立数据流、独立状态变化时拆（"可编辑文件打开"拆为"文件选择与类型识别"+"内容解析与资源加载"）
   - 多条实现需求可合并一条：共享同一机制/对象/文件格式/不可分割流程（删除确认+删除操作合并；撤销+重做合并为一条历史栈设计）
   - 公共机制提取为公共模块条目：横跨多子工具的机制只设计一次（索引/标识唯一性检查合并 6 条需求为一条公共设计，来源列全部编号）
   - 不为凑数拆分，不脱离需求加通用设计

## 单层 SRS 适配（非目标项目）

SRS 无用户/研发/实现三层（如单层个人站项目：全部 REQ-F + NFR 单层、无 Derivation 分层字段）时：

- 全部 REQ-F/NFR 都可作为【需求来源】；无"仅实现需求派生"限制
- 条目格式按用户示例：四字段（编号 / Title / Description / Source），不引入【设计要求及约束】字段——用户明确非目标项目不沿用（"这和目标项目没关系"）
- 工程结构、路由、数据模型等无直接 REQ 对应的架构内容放常规章节，不强行塞入 SD 条目
- 公共机制（多语言/搜索/API 集成/构建部署）作为 SD 条目承载多条相关 REQ，追溯矩阵注明覆盖说明
- 条目引用块风格与 SRS 保持一致（编号 + Title/Description/Source，字段名独占一行）

## 需求解析阶段（正式设计条目生成前）

部分任务要求先输出"需求解析清单"、经用户确认后再生成设计条目（目标项目实测流程：需求解析 → 确认映射 → 设计条目）。解析是设计派生的前置闸门：输出 14 字段逐条清单，不生成四字段正式条目；用户确认前不进入设计条目编写。

### 14 字段模板（逐条）

需求编号 / 需求名称 / 主要内容 / 用户·角色·外部系统 / 功能触发条件 / 主要输入 / 主要处理过程 / 主要输出 / 关键业务规则 / 数据·状态变化 / 模块·外部交互 / 主要异常·失败 / 需求关联 / 是否需要形成设计条目

### 解析要点

- **全局公共语境声明一次**：角色（如"用户"）、外部系统清单、触发默认形态、设计条目判定默认规则先总述，条目内只写差异。137 条清单全量展开会重复大量同值字段，审阅价值为零。
- **待确认事项清单**：编号列表 + 影响范围（如"F-277 Description 为空""可编辑文件范围跨层不一致"）。文档异常进待确认，不自行补全。
- **相似/重复需求关系表**：同子工具成对用户需求（概述 vs 具体化）、父→子分解、跨子工具同型实现需求（列模式组，如删除确认 6 工具、默认索引分配 6 工具、声明一致性 6 工具）、撤销/重做成对。保留全部编号，不删除。
- **研发需求→实现需求映射汇总表**：直接作为后续设计条目映射依据；无实现子需求的研发需求（典型：性能/容量类 F-119~123）标注覆盖风险，不硬塞设计条目。
- **同型条目用"同 REQ-F-XXX 模式 + 实体差异"**：逐条出现但内容不逐条复制；每条的独特字段（实体、属性、异常、关联）完整列出。
- **设计条目判定（解析阶段即给出）**：用户/研发需求→否（由下游承载）；实现需求→是（设计阶段可合并/公共提取，不按 1:1 强制）；性能/容量研发需求无实现子需求→否（覆盖风险；**用户显式决议直接派生时除外**——实例 F-119~123 分别编写 5 条，来源=研发需求编号）。

### 交付形态

完整清单写文件（write_file 整写，长文档分段用 patch 追加），对话输出紧凑版逐条（每条一段、分号分隔字段）；两版同源。137 条 × 14 字段全量 inline 超出单响应输出上限，紧凑版 + 文件是审阅可用形态。

### 常见坑

- 编号断档非缺失：SRS 编号按需求库分配、非章节顺序（实测 F-418 先于 F-287 出现、F-006 缺失）；解析保留原始编号，不补号不合并。
- Title==Description 占位条目（如 REQ-F-277）：按 Derivation 语义理解并标记待确认，不编造正文。
- 跨层范围不一致（如可编辑文件 F-007 三工具 vs F-062 五工具）：进待确认并提示范围扩展，不静默跟随某一层。

### 待确认问题清单（过滤规则）

解析清单的"待确认"经用户逐条决议后，若仍有影响条目编写的开放点，输出问题清单（如 `待确认问题清单` 章节）：
- 按需求编号分类；每条说明影响的设计内容（影响哪些设计条目/模块）
- 只列确实需要业务/技术人员确认的问题；不列类/方法/数据库字段/框架选择等技术细节
- 不影响当前设计条目编写的细节不列为阻塞问题
- 不自行给出未经确认的业务结论；已决议项不再重复列出
- 需求文本存在两种口径时（如"阻止生成整个文件" vs "排除失败条目"），列出冲突原文作为问题依据

### 需求→设计条目映射表（7 字段）

用户确认解析后，先建映射表（如 `*-需求-设计条目映射表.md`），批准后再写正式条目。每条目 7 字段：
拟定设计编号 / 拟定设计名称 / 设计范围 / 对应需求编号 / 拆分或合并理由 / 与其他设计条目的关系 / 是否存在待确认内容。

拆分合并原则：
- 一条目 = 一个相对独立、边界明确的功能或处理过程；复杂需求可拆为多条
- 多个紧密相关且处理过程一致的简单需求可合并；避免过度拆分完整功能、避免无关功能合并
- 异常处理通常合并到所属功能条目中
- 权限、日志、安全和性能要求一般在其影响的功能条目中体现，不单独成条目（**用户显式决议例外**：目标项目性能/容量 F-119~123 从研发需求直接派生、分别编写 5 条）
- 每个需求至少被一个设计条目覆盖；每个设计条目必须有明确的需求来源

表后分析必写四类 + 待确认：未覆盖需求 / 重复覆盖但可能需要合并的条目 / 范围过大的条目 / 范围过小的条目 / 仍需确认的问题。同型条目（各工具新增/删除/修改/预览/生成）按工具拆分不合并（自包含原则），在分析中注明"不合并"及理由。

### 映射覆盖验证

交付映射表前跑 scripts/check_mapping_coverage.py（解析 SRS 代码块、按 Source 前缀区分实现需求、扫描映射表来源列）：
- 实现需求全覆盖（91/91 类结论）
- 额外来源应为空，或恰为按决议直接派生的研发需求编号（如 F-119~123）

## 条目固定格式（只允许 4 个一级字段）

```txt
5.x.x.1 设计要求及约束
本小节是「设计约束 = 验收判据」，不是需求复述：回答"该设计必须保证什么、不得违反什么"，不回答"需求要求什么功能"（需求层），也不回答"怎么实现"（设计描述）。
填写四类：① 行为边界约束（必须保证/不得违反，含失败与异常路径）；② 判定性约束（可验证判据，如"生成结果仅包含当前配置存在的条目"）；③ 一致性约束（.c/.h 一致、预览与生成规则一致）；④ 机制性硬约束（删除/覆盖前必须经用户确认）。
句式用"必须/不得/应保证"判定式，每条 1~2 句、1~3 条。禁止"应支持 X"式功能声明（=需求 Description 照搬）。完整规范与实例见 references/design-constraints-writing.md；批量改写后用 scripts/check_constraint_copy.py 检测残留照搬。

5.x.x.2 设计

【设计编号】
SD-N

【设计名称】
<准确体现核心职责，避免空泛：文件管理/数据处理/相关操作 ✗>

【设计描述】
见「设计描述编写方法」一节。简单条目一段即可；复杂条目可加 Mermaid 图或数据流转表。

【需求来源】
REQ-F-XXX
REQ-F-YYY   <- 多条时逐行列出
```

- 设计编号 SD-1 起连续、唯一、不跳号（编号前缀按任务规格，SD-N / DES-XXX-### 都可能，以任务提示为准）
- 禁止机械改写需求（"系统支持日志导出并导出为CSV" 是复述不是设计）；描述要体现"怎么实现"
- 不编造技术栈/指标/字段定义/数据库/协议；SRS 未给的定量指标不写，用技术中立表达（文件加载模块、资源解析器）
- 描述里可自然融入输入校验、原数据保护、临时文件清理、失败时状态保持等，但不要机械套模板
- **四字段任务口径变体**：部分任务只要求【设计编号】【设计名称】【设计描述】【需求来源】四字段、不含"设计要求及约束"小节，描述必须单一自然段、无分级标题/编号列表/项目符号——以任务提示为准（实例：目标项目 2026-08 轮 61 条四字段交付；"只输出设计条目，不写封面/目录/引言/架构/术语/附录"）
- **引号块（``` 围栏）条目变体**：目标项目 2026-08 终版要求每条目用 ``` 围栏包裹（与 SRS 代码块式条目风格一致，围栏行不计入字段/段落检查）。解析按围栏分割：`r'```\n(【设计编号】\nSD-\d+\n.*?【需求来源】\n(?:F-\d+\n)+)```'`（re.S，捕获组 1=条目正文、2=编号——注意来源行 `(?:F-\d+\n)+` 是非捕获组，unpack 时只有 2 组）；模块标题（## 5.x）在围栏外，遇 `## ` 行先关围栏；该正则偶发漏块（实测 61/62，个别块因内部结构不匹配整块吞掉）——漏块时改用按行解析：`re.split(r'(?m)^```\n', text)` 取以【设计编号】开头的段，再按编号建 dict（稳健，推荐直接用）

## 设计描述编写方法（核心：回答 HOW，不回答 WHAT）

设计描述是唯一回答「软件内部怎么实现」的字段；「要做什么」由需求原文和「设计要求及约束」承载。检验标准：把设计描述删掉后，实现者若仍知道怎么编码 → 只是复述需求，不合格。

### 自包含原则（最高优先）

**设计条目必须自包含，不得引用兄弟功能条目的完整流程。** "整体处理流程与线型条目新增（SD-14）一致" = 把本条目核心内容外包给另一个功能条目，开发者被迫跳转才能理解；且被引条目一改，"一致"静默失效。对称功能条目（线型/线宽/色表/图像/字体/符号的新增/删除/修改）流程相似是事实，但每条各自写全流程——详细设计自包含优先于 DRY：重复是维护成本，跳转引用是理解成本，逐条实现的场景理解成本更贵。

### 引用边界（区分引用的是机制还是功能）

| 引用对象 | 例子 | 允许 | 理由 |
|---|---|---|---|
| 公共组件/架构词汇 | 编辑会话、命令机制、显示组件、撤销机制 | ✓ | 组件表已声明统一职责载体，读者已建立认知，无需跳转 |
| 子机制条目 | 默认索引分配（SD-23） | ✓ | 是本条目流程中的一个子步骤，读者不看也能理解主流程 |
| 对称功能条目 | 线型条目新增（SD-14） | ✗ | 整个流程外包，读者必须跳转才能理解本条目 |

### 主语与开头句原则（终版方案）

**主语 = 需求域实体（子工具 / 资源工具），设计描述中彻底不出现内部组件名。** 内部组件（线型工具条目管理组件、索引分配组件、预览显示组件等）是文档自己设计出来的抽象，出现即引发"是否要描述组件"的额外负担，偏离"从实现需求派生设计条目"的方向。主语映射：公共模块条目用"资源工具"，各子工具条目用对应子工具名（线型/色表/图像/字体/符号生成工具）。

**不写"X 由 Y 组件实现"独立总起句**——零信息：归属从章节位置 + 模块组件表已可得。首句承载「触发条件 + 首个动作」：

> 用户新增线宽条目时，线型生成工具创建线宽条目对象，通过默认索引分配机制（SD-23）分配默认索引值……（后续展开核心步骤 → 数据流转 → 结果状态 → 边界）

一句话承担的职责（以「线宽条目新增」SD-20 终版为例）：

| 句段 | 设计职责 |
|---|---|
| 用户新增线宽条目时，线型生成工具创建线宽条目对象 | 触发 + 需求域主语（子工具）+ 首个动作 |
| 通过默认索引分配机制（SD-23）分配默认索引值，设置默认线宽配置 | 核心步骤 + 子机制协作引用（带编号），回应需求"可识别的默认配置" |
| 条目以修改命令形式加入编辑会话，触发会话脏标记，并刷新条目列表显示 | 核心步骤 + 数据流转：命令封装→会话（脏标记）→显示刷新 |
| 新条目进入可编辑状态供用户修改 | 结果状态 |
| 新增操作可经撤销机制回滚 | 边界/恢复——与公共机制（撤销/确认/命令）的交互 |

**保留 vs 删除边界**：删除"内部组件名"（职责标签，不携带实现信息）；保留"实现机制"（编辑会话、修改命令、脏标记、撤销栈——设计实质）与"跨条目机制引用"（默认索引分配机制（SD-23）、复用公共修改保护机制（SD-6））。机制词是动词化行为，读者直接理解、不产生"描述它"的期待；组件名暗示实体、引发期待，是唯一的负担源。

**应包含**（按实际需要选取，非模板）：触发方式 / 关键处理步骤 / 数据流转与转换 / 模块协作（带 SD 编号）/ 结果状态 / 必要异常边界（失败是否终止、是否保留原数据、是否清理中间结果、用户得到什么）。组件归属以主语形式融入，不独立成句。

**禁止**：
- 复述需求原文或换说法
- 需求保持通配时枚举固定类型集合：图元库可配置（可增删元素类型）场景下，把几何属性写死为点/线/圆弧/椭圆/三角形五种的属性映射即属此类——设计描述须匹配需求通配性，按需求维度的类描述（如"按位置/尺寸/形状三类组织，属性集合与图元库中该元素类型的定义一致"），不固定绑定具体类型
- 引用兄弟功能条目流程（"与 SD-14 一致"类）
- "X 由 Y 组件实现"作独立总起句
- 代码级展开：类、方法签名、字段、错误码、完整状态机
- 编造定量指标（SRS 未给响应时间/容量/超时就不写）
- 擅自定技术栈；SRS 未指定时用组件表名称或技术中立词
- 简单条目堆砌统一模板（判断深度：简单一段话，复杂才分段+图）

### 组织方向：需求驱动，不以组件为模块（用户明确拍板）

设计文档的组织轴是"实现需求派生设计条目、按业务职责分模块"，**不是按组件组织**。用户曾探索按组件分章（组件表一行=一个章节），被明确否决：与"从 SRS 实现需求派生设计条目"的方向不一致（"不要以组件为模块"）。组件是设计描述中的职责载体/主语，不是组织单位。

- 组件表保留为**模块职责总览**（模块引言），不再被设计描述逐条引用，二者解耦——组件表改了设计描述不用跟着改，设计描述也永远不欠组件一个"描述"
- 不给每个组件开"组件设计章节"：组件行为实现已在 SD 条目中，逐组件章节必然重复，引入"行为驱动 vs 组件驱动"双组织视图
- 不设"组件协作概述"独立章节：用户关心的不是组件地图，而是每条设计描述能针对具体需求自包含、无额外负担。协作信息如确有需要，一句话融入模块引言即可

完整示例与合格/不合格对照见 references/design-description-writing.md。

### 格式规范审查（四字段口径 + 术语/对称扫描）

用户要求"只输出设计条目"时（四字段、描述单一自然段、无列表/标题），交付前跑结构审查脚本。实测要点（目标项目 2026-08 轮 61 条全量检查）：

- **解析按条目标题分割，勿按字段标签分割**：`re.split(r'(?m)^【设计编号】\n', text)` 会吞掉标签本身 → 61/61 误报"缺少字段"；改按 `^### SD-N 标题` 分割条目块后再解析四字段。
- **字段序列比较坑**：提取标签用 `【([^】]+)】`（无括号），比较基准须同步去括号，否则全量误报"字段序列异常"。
- **检查项**：字段标签序列恰为四字段 / 字段值非空 / 描述无空行分段、无 `- * •`、`1.`、`①` 标记、无 `#` 标题 / 编号唯一连续 / 需求来源逐行 `^F-\d+$` / 无编码级标记（class/SQL/new X() 等）。
- **术语一致性扫描**（比字段检查更常出问题）：同一概念跨条目多种叫法，实测"集成格式规格"(SD-22/23/30/36/42) vs "目标项目 标准格式规格"(SD-54) vs "外部规格"(SD-52/53) 三种并存——批量生成后必须全文扫术语，统一为一个主术语。
- **对称条目查"多出"不止查"缺失"**：对称审计除缺要素外，还查某一条独有的修饰（实测 SD-12 多出"以修改命令形式"，其余新增条目无）——同型条目表述必须要素对齐。
- **描述长度阈值**：复杂生成条目单段 ~290 字正常；>330 字（实测 SD-42=355、SD-54=337）偏长，共性句式（"生成过程遵循生成执行与结果管理机制，生成结果的保存遵循同名文件冲突处理机制"尾句）可精简合并。
- **条目外标题行**：文档标题行、模块标题（## 5.x）、条目标题（### SD-N）都在四字段之外；条目标题与【设计编号】+【设计名称】重复。实战结论（用户授权自决时按此执行）：删文档标题行与条目标题行、保留模块标题（## 5.x）作组织；去留本质是交付口径选择而非内容错误
- **审查输出形态**：通过项表格 + 按设计编号列问题（问题/修改建议），不重写全部条目；修订前先确认用户是否要修。

## 覆盖审查（评审视角：需求 ↔ 设计条目）

用户以评审身份要求覆盖审查时（八项检查：每条需求至少一条目覆盖含间接 / 语义承载非只填编号 / 异常覆盖 / 接口·权限·安全·数据·状态遗漏 / 无来源条目 / 来源填写错误 / 引用无关需求 / 重复设计），双轨执行：

- **机械矩阵（自己跑）**：设计条目来源集合 ↔ SRS 实现需求集合 ↔ 映射表来源集合三方比对。解析：SRS 代码块（Source 以 `REQ-F-` 开头=实现需求）、设计条目（按【设计编号】位置切片取 `^F-\d+$` 行）、映射表来源列（`^| SD-\d+ |` 行第 4 列）。检查：实现需求全覆盖 / 无来源条目 / 来源编号存在且层级合规（实现需求或已确认研发直接派生白名单，如 F-062、F-119~123）/ 需求被多条目引用集合为空。
- **语义审查（独立子代理 delegate_task）**：把已确认决议与"不判为错误"清单写进 context（用户/研发间接覆盖不算未覆盖、研发直接派生例外、业务决议补充内容不算虚构），让子代理逐条核对"设计描述是否真正承载需求核心语义"。重点方向：外部接口交互是否体现（实测缺口：符号工程文件条目只写了持久化与一致性，漏"供多进程 ARINC661 插件管理仿真工具加载并使用"——须补外部消费方语义）、异常/失败/无效处理、跨需求张力。子代理发现必须回原文复核后再采纳。
- **SRS 层跨需求张力裁决模式**：相邻需求可能口径冲突（实测：F-278 切换保持未保存修改 vs F-414 退出符号生成工具须提示）。识别后不自行定夺，显式提交用户裁决；裁决后修订设计描述 + 在决议记录登记（编号+裁决+影响条目）。用户裁决示例："退出符号生成工具即子工具切换"→SD-5 触发场景补"切换离开当前子工具（含退出符号生成工具）"、SD-1 改"切换不自动保存或丢弃，由保护机制按用户选择处理"。
- **审查输出结构**：未覆盖需求 / 部分覆盖需求 / 错误映射 / 重复设计 / 无需求依据的设计内容 / 建议修改的设计条目编号 + 八项检查逐项结论；不直接生成新条目；修订前先确认用户是否要修。

## 评审意见修改循环（设计条目修订）

评审反馈落地四步（实测多轮：评审意见 → 修改 → 复验，交付编号 61→62→63 连续演进，每轮一个决议号）：

1. **设计条目修改**：只改被点名条目 + 概念波及的相关条目。拆分 → 编号顺延/置换（见常见坑）；术语统一/概念澄清 → 逐个核对引用该概念的相关条目（实例："可编辑文件=资源条目载体"波及 SD-1/2/6/7/11 与六类新增条目；"符号资源条目引用工程文件"波及 SD-11/44/45/55；展示形式澄清"可编辑文件=资源表 / 工程文件=图形编辑器"波及 SD-11/44/55 与界面章节副标题），不只改评审点名的条目
2. **映射表同步**：总览 + 明细 + 分析区（3.2 非合并组、3.5 决议记录）一并更新
3. **解析清单登记新决议**：编号递增（实测 #25→#33），内容 = 评审裁决 + 影响条目编号；旧决议保留为历史记录
4. **复验清单**（全部通过才回复）：编号连续唯一 / 四字段×N / 围栏 2N / 覆盖（91/91 + 白名单研发例外）/ 设计来源=映射表来源 / 术语残留为 0 / 需求来源行无杂字

展示形式类表述与既有术语并存时用一次括注桥接（"图形编辑器形式（即符号编辑器）"），后续条目直接沿用。删除/级联类语义（实例：SD-45 删除符号条目**不**删除其引用的符号工程文件，工程文件仅由用户主动删除）以评审/用户裁决为准，勿自行推断级联删除。

## 协议/需求不可改时的设计描述修订（澄清驱动，用户确认模式）

技术协议原文不清晰、需求文档须响应协议故跟随偏差、两层均不可改时（目标项目 2026-08 实测），详细设计是唯一可澄清语义的层，受三重约束：

1. **追溯不变**：改后【需求来源】保持不变，仍响应原需求条目
2. **结构不变**：不删除/不新增设计条目，SD 编号与条数保持不变
3. **只改描述**：仅修改【设计描述】中与澄清语义不符的内容；其余不动

流程（用户批准的审阅模式，勿跳过）：

1. **先出对比文档，不直接改原文**：`详细设计-设计描述修改前后对比-YYYYMMDD.md`。结构 = 确认记录 / 澄清内容要点表（修改依据）/ 修改总览表（条目、修改类型、原因）/ 逐条对比（修改前/修改后/修改说明，用 `>` 引用块）/ 界面设计章节同步建议（涉 5.8 类非 SD 章节时单列）/ 明确不改条目及原因 / 待确认点表
2. **待确认点带状态**：✅ 已确认 / ⏳ 待确认；用户逐条确认后更新文档状态列，不批量自决。用户修正（如"工程文件也有标识但用户不可见"）必须回填到对应条目描述与修改说明，再进入下一轮
3. **用户确认后才改原文**；对比文档本身就是交付物，用户会自行阅读后决定下一步
4. **可选中间产物：修改后总览文件**——用户确认对比稿后、改原文前，常要求再出一份 `详细设计-修改后设计条目总览-YYYYMMDD.md`：只含被修改条目的**修改后完整文本**（四字段格式可直接替换原文），外加界面设计章节同步表格与快速索引表。用于"总览一遍修改后长什么样"，用户看完才授权改原文。未修改条目不列出（注明保持原文）

对比文档要点：修改说明逐条对应澄清点；"明确不改"条目也要列原因（防用户误以为漏改）；澄清内容要点按确认动态增补（如新增"工程文件内部标识"条目）。

### 目标项目 已确认语义（2026-08-11，影响 SD-1/11/44/45/46/47/55/56/57 及 5.8）

六类资源表统一模型、符号表↔符号编辑器↔符号工程文件多对一、工程文件内部标识（用户不可见）等已确认语义——写条目/改描述时直接引用，勿向用户重复确认。

## GJB 438B 交付 docx 的需求可追踪性表（章节号 ↔ 设计编号）

详细设计最终交付物是 `详细设计报告.docx`（GJB 438B 模板，正文含"设计要求及约束"小节 + 四字段条目、需求来源为 **SR-xxx** 编号），需补充第 6 章"需求可追踪性"的表 3：软件需求规格说明侧（章节号/需求）与软件设计说明侧（章节号/CSCI设计）。生成"章节号 ↔ CSCI设计"列的方法（实测 2026-08-11）：

1. **用 read_file 读 docx**（自动提取文本，~1200 行）；TOC（目录）是章节编号的权威来源——正文标题段落（pStyle 22/30）本身**不带编号文本**，编号是 Word 多级样式渲染的，只有目录里能看到真实编号（5.2.1 公共机制、5.2.2 目标项目 线型生成工具…5.2.7 性能与容量）。
2. **章节粒度以 TOC 为准**：SD 归属按 TOC 列出的最小章节号；正文中的分组小标题（如"线型""线宽"用 style 4=设计条目标题样式，不是标题层级）**不产生独立章节号**——线型/线宽两组 12 条 SD 全部归 5.2.2。若用户要更细粒度（5.2.2.1/5.2.2.2），需显式确认后另做。
3. **docx 内部结构确认**（提取文本看不到层级时）：`unzip -o docx word/document.xml`，正则抓 `<w:pStyle w:val=...>` + `<w:t>` 文本，pStyle 映射：1=章标题、22=节标题、30=小节标题、4=设计条目标题、5=设计要求及约束/设计、afd=正文。TOC 条目 pStyle 为 TOC10/TOC20/TOC3。正文标题段落无 numPr/outlineLvl（编号在 Word 列表样式中），不要据此判层级。
4. **CSV 输出**：两列 `章节号,CSCI设计`，每个 SD 一行（64 行+表头），存 `需求可追踪性-章节号-CSCI设计.csv`。注意提示用户：SRS 侧两列（章节号/需求）需按 SRS 实际章节号自行填写，本 CSV 只覆盖软件设计说明侧。
5. **编号体系差异提醒**：docx 正文【需求来源】是 SR-xxx，md 原文是 F-xxx——同一条目在两种载体编号不同，交付 CSV/表 3 时以 docx 现状为准，不要用 md 的 F-xxx 去对。

## 同类条目对称性审计（设计描述质量）

批量生成/改写后，按**行为类型骨架表**审计同类条目的要素对称性——同类型条目（线型/线宽/色表/图像/字体/符号的新增、删除、修改……）必须覆盖相同要素，否则读者分不清是设计差异还是漏写。骨架表（每类行为的必须要素，审计基准）：

| 行为类型 | 必须覆盖要素 |
|---|---|
| 新增 | 触发 → 创建对象 → 索引/标识分配 → 默认配置 → 命令封装 → 会话脏标记 → 列表刷新 → 可编辑状态 → 可撤销（+工具特有：图像/字体待导入、符号可放置元素） |
| 删除 | 确认提示 → 命令封装 → 移除内容 → 脏标记 → 刷新 → 可撤销 → 取消分支 |
| 修改 | 输入变更 → 命令写入 → 记录前后值 → 预览/列表刷新 → **即时校验策略** → 配置进会话 |
| 索引/标识分配 | 扫描已用 → 选最小值 → **仅初始化**（用户可改） → 唯一性交 SD-8 |
| 预览/外观显示 | 纯显示声明 → 绘制依据 → 自动重绘 → 与生成规则一致 |
| 校验 | 注册为生成前规则 → 遍历 → 检查项 → 标识问题 → 阻止生成 → 随生成重算 |
| 生成 | 流水线 → 遍历 → 组织数据 → .c/.h → 双重一致性 → 集成格式 → 临时文件 → 失败处理 |

审计流程：① 建骨架表 → ② 自动关键词检查（每要素配关键词/正则）→ ③ **人工甄别误报** → ④ 按问题模式归类输出报告（不逐条零散报）→ ⑤ 同类一起修复，修复后重跑验证。

已知误报两类（自动检查必出，必须人工甄别）：关键词缺"依据"≠缺绘制依据（如"优先按原始像素数据渲染""按条目当前绑定的字体渲染"就是绘制依据）；名称含"有效性检查"≠生成前校验规则（导入时校验如 TTF 有效性检查属 REQ-F-299，不需要"注册/阻止生成/重算"要素）。完整骨架表细节与本次审计实例见 references/design-description-audit.md。

## 设计要求及约束照搬审计

"设计要求及约束"是照搬需求的重灾区（实测 66 处中 52 处与 SRS Description 相似度 >0.8，24 处 1.00 一字不差）。检测方法：约束正文与对应【需求来源】的 SRS Description 去空白后做 difflib.SequenceMatcher 相似度，>0.8 = 基本照搬需重写。重写判据与七类骨架句式见 references/design-constraints-writing.md；自动检测脚本 scripts/check_constraint_copy.py（同时匹配 4 级 `#### X.X.X.1` 与 5 级 `##### X.X.X.X.1` 约束标题，否则漏 SD-1 类条目）。

批量改写按模块分批（公共→线型→色表→图像→字体→符号），每批独立跑验证（编号连续 / 引用不丢 / 四字段 / 旧句式残留），全部完成后全量核查约束章节"应支持/应检查/应显示"式功能声明残留为零（实测 67 处约束一次改造通过）。

## UI 界面设计覆盖（5.7 模式）

详细设计常缺表现层：行为/机制条目齐全但开发者不知道界面长什么样。交付级评估若发现 UI 未覆盖，新增独立章节（如 `## 5.7 界面设计`）集中覆盖——不把 UI 元素塞进四字段条目（界面是横切关注点，且破坏条目对称）。

结构（目标项目验证过）：
- 总体布局：主窗口区域表（区域 | 内容 | 关联设计条目），如导航区 / 工作区 / 状态区
- 公共交互模式：按交互流程分小节（打开文件、未保存提示、撤销/重做、生成与保存、失败反馈），每小节引用对应 SD 条目
- 每子工具界面表：界面区域 | 界面元素 | 职责 | 关联设计条目（如条目列表区 / 属性区 / 预览区 / 信息显示区 / 画布编辑区 / 图元库面板）

规则：
- 界面元素必须可追溯到现有 SD 条目（关联列填 SD 编号），**不新增功能**：新章节不得引入任何 REQ 编号（验证项：新章节内 REQ-F 出现次数应为 0；**例外：用户显式决议指定章节需求依据时——实例 REQ-F-061/F-376→5.8 界面设计——允许在章节引言注明依据 REQ，用户决策优先于"0 REQ"规则**）
- 纯章节非设计条目：不产生 SD 编号，不破坏 68 条四字段体系与 91↔91 引用
- 菜单 / 快捷键 / 对话框形态是界面设计决策，可自由定，但入口必须已有需求依据
- 验证：新章节 SD 引用全部落在 1~68；表格列数一致（总体布局 3 列、子工具表 4 列）

## 长文档分段写入

- 内容长（几十个条目）时：write_file 写首段 + patch 以文件尾唯一锚点追加后续段
- 锚点用上一段末尾唯一字符串（最后一个【需求来源】编号），确保 old_string 全局唯一
- 全部写完后再跑验证脚本，不要边写边猜

## 常见坑

- 需求层标题可能改名（"具体实现子需求"→"实现需求"）：以 SRS 章节标题 + Source/Derivation 字段判定层级，不靠旧记忆
- Description 为空的需求（Title==Description 占位）：用 Derivation 字段语义设计，不编造额外规则
- 性能/容量类需求常在研发层无实现子需求 → 作为覆盖风险提示用户，不硬塞设计条目（若用户显式决议直接从研发需求派生，则以决议为准，【需求来源】填研发需求编号，实例 F-119~123）
- 任务提示中的编号/格式只是示例；实际编号、实际三层名称从 SRS 提取
- 跨层范围不一致要显式提示：用户需求/技术协议范围 ≠ 研发/实现需求范围时（实例：可编辑文件覆盖线型/色表/符号 vs 扩展至全部五工具），按实现需求设计但向用户提示范围扩展，不静默跟随
- SRS 实现需求解析坑：Source 字段行形如 `REQ-F-062（可编辑文件管理）` 是父需求引用，不是实现需求；解析必须整行锚定（`^REQ-F-\d+$`），否则"漏设计"检查误报（本会话实测 120 vs 91）。同时注意模块边界是 `##` 级标题，停止收集不能只看 `###`
- 中文路径项目（如 `多进程目标项目Server设计工具-需求`）下 search_files/rg 不可靠：可能报 MSYS 路径转换错误（os error 3），也可能**静默返回 total_count: 0**（无报错、看似"无匹配"——实测 pattern='*.md' 和 '*' 都空，比报错更危险）→ 先用 `terminal ls -la` 确认文件存在，再用 read_file 绝对路径直接读；批量验证用 python 脚本（execute_code 或 scripts/），不依赖 rg
- 约束小节数与条目数可不相等：SD-2/SD-3 共用一个"设计要求及约束"小节时按小节审计，勿按条目数硬对齐（68 条目 ≠ 67 小节）
- 可理解性审查（开发视角 10 项：模糊词扫描/复述检测/术语消歧/默认配置构成/容量判据/失败模式措辞）、横向一致性审查（10 项：术语变体盘点/机制引用名对齐/枚举简称/规则悬挂/对称要素不对称/来源编号）与最终交付检查（13 项）的完整清单见 references/design-entry-review-checklist.md（五轮：格式规范/覆盖/可理解性/一致性/终检）；每轮均为独立子代理 + 脚本机械核对交叉验证，结论须回原文复核
- patch 工具可能插入 LF 行尾到 CRLF 文件 → 批量修改后统一行尾（\r\n 归一）
- **条目拆分导致全链编号顺延**：评审反馈拆分条目（实例：SD-3 拆为"可编辑文件新建"+"可编辑文件打开"）后其后全部编号 +1（61→62 条），必须同步 ①设计条目块内【设计编号】文本——重排放置顺序时只改顺序不改块内编号文本 → 旧块保留旧编号出现重复编号（实测旧 SD-4 块仍写 SD-4，后续全部错位）②映射表总览+明细 ③支持文档（解析清单）决议/引用 ④界面设计章节 SD 引用。全库移位正则 `SD-(\d+)` 只命中带 "SD-" 前缀的数字：斜杠简写组（SD-46/47/50）与波浪号范围（SD-12~16）只移首个数 → 需补 `(SD-\d+)((?:[/~]\d+)+)` 后缀移位（N≥4→+1），"~"范围两端点都要移；已移过的 "/" 组勿再套移位（会双重移位，需回退 N≥5→-1）
- **子章节分组重排 = 置换式重编号，勿用算术移位**（实例：5.2 拆 5.2.1 线型 SD-13~18 / 5.2.2 线宽 SD-19~24，置换 14→19、15→14、16→20…10 个号变）：①置换必须**单遍正则 + dict 查表**（`{14:19,15:14,...}`），不能 +1/-1 算术；②斜杠简写组与波浪号范围的后缀数字**同样要过 dict**——置换轮实测 "SD-19/20/28/36/42" 只换了首个数、后缀残留旧号（与移位轮同一陷阱复发）；③重建映射表按"名称→新号"排序后整表重建，不要原位手术（首版重建把 13~24 行排到表尾）；④置换后校验：每个斜杠组/范围与**期望 frozenset 组集**比对（新增组/删除组/修改组/预览组/校验组/生成组/画布组按新号推导），例举对列表（如 3.2 分析表 "SD-13/14、14/15、24/25…"）会被置换打乱，需显式重写成合法新号对；⑤模块边界不变时（5.2 仍含 13~24）只需重建章节内部顺序，其余章节不动
- **顺延/置换变换通用陷阱（三次变换同一组坑复发）**：①单遍组感知正则 `re.sub(r'SD-\d+(?:[/~]\d+)*', fn, text)` 一次处理斜杠组+波浪号范围（fn 对组内每个数字按规则移位/查表），避免"先移前缀再补后缀"两遍法——第二遍会把已移好的 "/" 组再移一遍需回退（N≥5→-1），SD-3 拆分、线型/线宽置换、SD-51 复制粘贴拆分三次都踩；②变换脚本先 transform 后 write，assert 失败在 write 前中止、文件保持原状——assert 目标串以文件**当前实际状态**为准，勿拿"预期变换后"的串断言未变换的文件；③write 后扫【需求来源】行尾杂字（实测 "F-306请" 使覆盖检查漏 1 条）：`【需求来源】\n((?:F-\d+\n)+)([^\n`]*)` 的 tail 必须为空；④变换后核对分析区行数未减（映射表 3.2 非合并组行可能在重建中静默丢失，实测两行消失）——勿只验证总览/明细；⑤每次顺延/置换后输出"旧→新"编号对照表交用户核对
