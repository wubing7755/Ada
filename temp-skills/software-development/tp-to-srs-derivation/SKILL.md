# TP-to-SRS Derivation（从技术协议派生 SRS）

当用户提供一份技术协议（TP / Technical Protocol）并要求编写 SRS 时使用本技能。特别适用于航空电子、嵌入式显示等领域的技术合同需求分析。

## When to Use

- 用户提供一份技术协议（.md/.docx）并要求编写 SRS
- 用户说「基于这份协议写一份SRS」
- 从合同/协议条款中系统化派生出软件需求

## TP-to-SRS 工作流

### Phase 1: 阅读与理解

1. 完整阅读 TP 文档，建立产品全景
2. 明确：有多少个系统/子工具、它们之间的上下游关系
3. 识别 TP 中所有的「要素」：界面、功能、文件格式、交互流程

### Phase 2: 向用户确认架构决策

在开始编写 SRS 之前，必须向用户确认以下决策。这些决策 TP 通常不会涉及，但会影响需求的派生：

| 问题 | 说明 |
|:----:|------|
| 部署方式 | 单机 / 网络 / B/S 架构 |
| 前端框架 | 如 Blazor WASM、Vue、React |
| 后端框架 | 如 ASP.NET Core、Node.js |
| 多个系统的关系 | 独立应用 / 同一平台的不同模块 |
| 系统间交互方式 | 文件传递（本地保存后导入）/ API 调用 / 共享后端存储 |
| 各系统是否共享后端 | **必须明确询问**：这是两个独立的完整 B/S 系统（各有独立前后端），还是共享同一后端的不同前端。默认假设为独立系统 |
| 用户认证 | 需要登录吗？权限管理？是实际鉴权还是仅作为启动入口？ |

先输出规划方案，待用户确认后再正式撰写。

### Phase 2.5: 完整的起草工作流（从确认到交付）

架构决策确认后，按以下顺序起草 SRS：

1. **起草 §§1-2（引言+总体描述）**：术语表、架构图、功能概览、约束假设
2. **起草 §3 公共需求**：登录入口等跨系统公共需求
3. **起草 §4 系统 A 功能需求**：按子工具分组，提取公共模式
4. **起草 §5 系统 B 功能需求**：界面布局、主要功能、文件交互
5. **起草 §6 系统间交互**：文件传递、前后端通信
6. **起草 §7 非功能需求**：性能、兼容性、可靠性、可维护性、安全
7. **起草附录**：变更记录、需求统计表、追迹矩阵
8. **格式校验**：检查编号连续性、围栏配对、优先级一致性
9. **统计校验**：确认附录统计与头部一致，用 Python 脚本逐行提取需求头部

**需求编号**: 两种方案可选：

| 方案 | 编号格式 | 适用场景 | 优缺点 |
|:----:|:--------:|:---------|:------:|
| **全局连续** | `REQ-F-001 ~ REQ-F-051` | 需求数 < 100，章节结构稳定 | 简单直观，但新增需求只能追加末尾 |
| **百位区间** | `REQ-F-0100~0199`（TP §1.2）、`REQ-F-0200~0299`（TP §1.3）... | 需求数 > 100，需清晰追踪各 TP 来源 | 一眼可知来源，区间内可灵活增补，但编号号码较大 |

**百位区间编号方案**（适用于大规模 SRS，约 100+ 条需求时推荐）：

| 编号区间 | 用途 |
|:--------:|:----:|
| REQ-F-0001~0099 | 公共需求（登录、可编辑文件生命周期） |
| REQ-F-0100~0199 | TP §1 资源工具 + 界面框架 |
| REQ-F-0200~0299 | TP §1.3 色表生成 |
| ...以此类推，每百段一个 TP 条款 |

- 区间不必连续填满，留有扩展空间
- 增补时在对应区间内按现有最大号+1 即可
- 附录 B 按区间统计，附录 C 按区间关联 TP 条款

一次选定方案后避免再做大规模重编号。

### Phase 3: 六条派生路径

| 路径 | 说明 | 应用场景 |
|:----:|:-----|:---------|
| **直接映射** | TP 条款直接对应一条需求 | TP「提供图形人机交互界面」→界面布局需求 |
| **拆分细化** | TP 一个条款拆为多条需求 | TP「生成 .c/.h」→参数配置 + 文件生成 + 编译兼容（多条） |
| **跨子工具提取公共** | 多个子工具共享特性的公共需求 | 多个子工具都生成 .c/.h → 公共文件生成规范 |
| **架构衍生** | 从已确认的架构方案派生 | B/S → 登录入口、前后端通信、文件上传、后端渲染 |
| **精度修正** | 初版 SRS 完成后逐句回归 TP，修正首次编写的表述精度 | TP「过程中同步」→修正 AC 时序；TP「线型」→补充线型类型选择 AC |
| **AC 原子化拆分** | 将粗粒度需求中独立的 AC 条件提升为独立需求 | 原一条「线型.c/.h 文件生成」→拆为：.c 生成 / .h 生成 / A661 格式 / 编译兼容 / 索引获取 / 空配置校验 共 6 条 |

**约束**：
- 前四类在首次编写阶段使用
- 第五类（精度修正）在用户要求进一步检查时使用，不新增 REQ-F 条目
- 第六类（AC 原子化拆分）在用户明确要求细化粒度时使用，**不主动做**——默认保持适中粒度

### Phase 4: 需求条目编写

### Phase 4.0: 子工具需求的三层组织结构

对每个子工具（线型、色表、图像、符号、字体等），按三层组织需求，确保覆盖完整、无重叠：

| 层级 | 包含内容 | 典型 Actor | 示例 |
|:----:|:---------|:----------:|------|
| **配置层** | 用户输入/导入/配置参数的功能 | Application Developer | 线型条目添加、占空比配置、颜色选择 |
| **生成层** | 系统处理、生成文件、校验的功能 | Application Developer | .c 文件生成、.h 文件生成、A661 格式、空校验 |
| **验证层** | 生成结果的外部验证（编译、运行时） | Verification Engineer | 编译兼容性、按索引获取正确性 |

**分层原则**：
- 配置层 = 用户做什么 → 每条配置操作独立为一条需求
- 生成层 = 系统做什么 → 生成、输出、校验各一条
- 验证层 = 外部验证 → 每条验证场景独立为一条需求
- 配置层和生成层的 Actor 通常为 `Application Developer`，验证层为 `Verification Engineer`

**拆分示例**（TP §1.2 线型生成）：

```
原一条「线型 .c/.h 文件生成」→ 6 条独立需求：

配置层:
  REQ-F-0104 线型条目添加           (用户添加条目)
  REQ-F-0105 线型占空比配置         (用户配置占空比)
  REQ-F-0106 线型类型选择           (用户选择类型)
  REQ-F-0107 线宽配置              (用户配置线宽)
  REQ-F-0108 线型颜色配置          (用户选取颜色)
  REQ-F-0109 线型条目管理          (查看/修改/删除)

生成层:
  REQ-F-0110 线型生成空配置校验     (异常校验)
  REQ-F-0111 线型 .c 文件生成      (.c 输出)
  REQ-F-0112 线型 .h 文件生成      (.h 输出)

验证层:
  REQ-F-0113 线型文件编译兼容性     (编译验证)
  REQ-F-0114 线型按索引获取正确性   (运行时验证)
```

### Phase 4.1 需求条目格式

每条需求使用以下 **结构化格式**（用户偏好，经多轮验证）：

```markdown
### REQ-F-XXX 🔴 [Actor: Application Developer]

**Title**
<中文标题，一行>

**Description**
<中文功能描述，说明系统应做什么行为>

**Acceptance Criteria**

AC1：<中文场景名称>

Given <英文前置条件>
When <英文触发操作>
Then <英文预期结果>
And <英文附加结果>

AC2：<中文场景名称>

Given <英文前置条件>
When <英文触发操作>
Then <英文预期结果>
```

格式要点：
- 需求编号 **用 `###` 标题级**（非内联加粗），便于自动提取
- 优先级符号 **放在编号后**：🔴 P0 / 🟡 P1 / 🟢 P2
- Actor **用方括号**，格式为 `[Actor: RoleName]`
- Title/Description/Acceptance Criteria **各为独立段落**，用 `**粗体**` 作为段落标题
- 每个 AC **必须有场景名称**（如 `AC1：显示登录界面`），不可只写 `AC1：`
- Given/When/Then **使用英文**，各自独立一行
- 多角色需求，Actor 之间用逗号分隔：`[Actor: Application Developer, Verification Engineer]`
- **整个需求条目必须用代码围栏（`````` ` ` ``` ``）包裹**，围栏内包含从 `###` 标题行到最后一个 AC 的全部内容。这样便于阅读时快速定位需求边界，也方便后续程序化提取

完整格式示例：

````markdown
```
### REQ-F-001 🔴 [Actor: Application Developer]

**Title**
Tab 导航布局

**Description**
系统应在主页面顶部展示 Tab 导航栏。

**Acceptance Criteria**

AC1：Tab 导航栏

Given 用户登录后进入主页面
When 页面加载完成
Then 顶部应显示所有子工具的 Tab 标签页

AC2：Tab 切换

Given 用户正在某个 Tab 中操作
When 用户点击其他 Tab
Then 应切换至对应工具的操作界面
```
````

### Phase 4.2 优先级定义

优先级符号 MUST 用于需求头部，不得仅定义在 §1 的约定表中：

| 符号 | 优先级 | 含义 |
|:----:|:------:|------|
| 🔴 | P0 — Mandatory | 必须有 — 系统不可用或无法交付 |
| 🟡 | P1 — Desirable | 建议有 — 缺失会显著降低可用性 |
| 🟢 | P2 — Optional | 可以有 — 增强功能 |

### Phase 4.3 常用 Actor

| Actor 名 | 对应角色 | 常见需求范围 |
|:--------:|:--------:|-------------|
| `Application Developer` | 应用开发工程师 | 使用资源工具，操作各子工具，生成文件 |
| `Verification Engineer` | 测试/验证工程师 | 验证生成文件格式正确性，预览效果 |
| `System Integrator` | 系统集成工程师 | 工程文件管理，DF 导入导出，工具间交互 |

### Phase 4.4 需求格式参考示例

参考 `references/requirement-format-example.md` 获取完整的格式示例。如需更详细的格式规则（围栏配对、AC 编号、语言约定等），另见 `srs-requirement-format` 技能。

### Phase 5: 多系统 SRS 章节结构

当 SRS 覆盖多个独立但交互的系统时：

| 章节 | 内容 |
|:----:|------|
| §1 | 引言（目的、范围、术语表、文档约定、系统架构） |
| §2 | 总体描述（产品全景、功能概览、用户特性、约束、假设） |
| §3 | 公共需求（登录入口等两个系统共享的需求） |
| §4 | 系统 A 功能需求 |
| §5 | 系统 B 功能需求 |
| §6 | 系统间交互需求 |
| §7 | 非功能需求 |
| 附录 | 变更记录、需求统计表、追迹矩阵 |

### Phase 6: 追迹矩阵维护

附录 C 必须包含 TP 条款 → SRS 需求的映射表：

```markdown
| TP 协议条款 | SRS 需求 |
|:-----------:|:---------:|
| TP §1.x xxx | REQ-F-001 |
| 衍生：B/S 架构 | REQ-F-033~036 |
```

- 每条 TP 条款都被覆盖 → 证明无遗漏
- 架构衍生项标注「衍生：xxx」→ 与协议派生项区分

### Phase 7: 统计校验

编写完成后，通过 Python 脚本或 grep 统计：

1. 从需求头部提取编号、优先级、角色
2. 与附录 B 统计表逐项比对
3. 确保 🔴🟡🟢 计数与表一致
4. 确保总需求数 = 各章节之和

### Phase 7.5: 来源标注

每个需求条目末尾（关闭 ``` 围栏之前）添加一行来源标注，指明该需求对应 TP 的哪个条款：

```
> **来源**: TP §1.2
```

格式规范：
- 直接映射需求标注 `TP §x.x`
- 拆分派生需求同样标注 `TP §x.x`
- 架构衍生需求标注 `无（衍生：xxx）`
- 从 AC 独立出的子需求标注 `TP §x.x（自 REQ-F-XXX 派生）`
- 来源行放在关闭 ``` 围栏之前，即最后一个 AC 之后、``` 之前的位置

来源标注与附录 C 追迹矩阵应保持一致。

### Phase 8: 自进化检查（可选）

如果用户要求对 SRS 进行自进化质量检查，请参考 `references/srs-self-evolution.md`，聚焦三个维度：

1. **术语一致性**：全文术语与 §1.3 术语表一致
2. **AC 可测试性**：每条 AC 的 Given/When/Then 明确可测，无模糊词
3. **边界案例遗漏**：检查每条需求是否遗漏异常/边界场景

执行流程：
- 先读全文档 → 分析三个维度 → 输出发现清单
- 让用户确认哪些需要修正 → 修正 → 验证统计一致性
- 通常 1 轮已足够，已收敛则停止

### Phase 9: 多轮自进化迭代模式

当用户要求「继续自优化」时，按轮次推进，每轮切换审视维度，避免重复检查同一维度：

| 轮次 | 聚焦维度 | 典型产出 |
|:----:|:---------|:---------|
| **第 1 轮** | 边界案例遗漏 + AC 可测试性 | 补充异常场景 AC，修正模糊词 |
| **第 2 轮** | 需求间交叉引用 + 单 AC 需求扩充 | 补充「参见 REQ-F-xxx」引用，为粒度过粗的需求补充 AC |
| **第 3 轮** | TP 原文逐句回归 + 架构一致性 | 回读 TP 每一行，找首次遗漏的可派生点；检查架构描述与实际是否一致 |
| **后续** | 收敛判断 | 如第 3 轮改动量 < 5% 即停止；否则继续仅针对第 3 轮发现修正 |

**收敛标准**（定性与定量结合）：
- 定量：连续两轮改动量 < 5%（新增+修改行 ÷ 总行数）
- 定性：**TP 原文逐句回归**——逐行通读 TP.md，检查每句是否有对应的 SRS 覆盖，无遗漏可派生点
- 同时满足两个标准 → 文档已收敛，停止进化

**重要实践**：第 3 轮（TP 逐句回归）的发现量通常远少于前两轮，这是正常现象。目标不是找到越多越好，而是确认无遗漏。如果第 3 轮找到 8~12 个点，说明第 1~2 轮质量不错但还没饱和；如果找到 0 个，建议回看是否遗漏了深层派生。

### Phase 10: TP 逐句回归（第五类派生路径）

在初版 SRS 完成并且用户要求进一步检查后，执行 TP 原文的**逐句回归**——逐行通读 TP.md，标记每个条款的 SRS 覆盖情况。这实际上构成了**第五类派生路径**——精度修正派生：

| 路径 | 说明 |
|:----:|------|
| **⑤ 精度修正** | 重新审视已覆盖的 TP 条款，发现首次编写时的表述精度不足，修正 AC 时序、补充遗漏属性、细化工作流描述 |

精度修正不增加新需求（REQ-F 数量不变），而是通过修改 AC 内容、补充缺失的 AC、或修正 Description 来提升文档对 TP 的忠实度。

常见精度修正模式见 `references/srs-self-evolution.md` 的「常见遗漏派生点模式清单」。

| 需求标题/描述 | 中文 | 行为描述 |

| Actor 角色名 | 英文 | 如 Application Developer |

## 常见陷阱

### 1. 过度偏离 TP
**症状**：引入了用户协议中未约定的功能。
**对策**：所有需求应能从 TP 中找到直接或间接依据。架构衍生需求必须经用户明确确认。

### 2. 遗漏跨子工具公共需求
**症状**：每个子工具重复定义相同的生成规范。
**对策**：在书写前先横向扫描各子工具，提取共同的交互/输出模式。

### 3. 统计表与需求头不一致
**症状**：附录统计写 P0=27，实际头部只有 26 个 🔴。
**对策**：用 Python 脚本从需求头部正则提取，自动生成计数。

### 4. Given/When/Then 语言混用
**症状**：同一文档中有的 AC 用英文、有的用中文。
**对策**：在 §1 文档约定中明确约定，全文统一。

### 5. 假设多个系统共享后端
**症状**：TP 描述了多个独立工具，SRS 错误假设它们共享同一个后端服务/同一数据库。
**对策**：
- 在 Phase 2 中必须明确询问多系统的部署关系和交互方式
- 除非用户明确说「共享」，否则默认视为独立系统，各有独立后端
- 工具间的文件交换通常通过本地文件系统完成
- 架构图中应描绘清楚每个系统的独立边界

### 6. 需求编号格式不匹配用户预期
**症状**：用户要求 `REQ-F-XXX` 格式而非 `REQ-{类别}-{序号}` 格式。
**对策**：TP 派生场景下默认使用全局连续编号 `REQ-F-XXX`，不作按类别的分段编号。避免在编写后再做大规模重编号。

### 7. 登录入口需求优先级模糊
**症状**：§3 公共需求的登录入口需求不知道该标 🔴 还是 🟡。登录界面是启动入口但没有实际鉴权，系统缺少它仍然可用。
**对策**：登录入口需求（非实际鉴权）应标为 **🟡 P1 — Desirable**。只有在 TP 明确要求强制身份验证时才标 🔴 P0。

### 8. 架构图未能体现系统独立边界
**症状**：多系统场景中，架构图画成了共享同一个后端的结构，而用户明确表示它们是独立系统。
**对策**：
- 架构图必须对每个系统画独立的竖列（前、后端的独立边界），而不是把多个前端画进一个共享后端框
- 独立系统之间的文件交换用横向箭头标注「保存到本地 → 导入」，不经过共享后端
- 每个后端标注其专有职责（例如：后端 A = .c/.h 生成 + .dll 渲染；后端 B = DF 生成 + 文件解析）

正确示例（两个独立 B/S 系统）：

```
┌────────────────────────────────┐  ┌────────────────────────────────┐
│         系统 A                  │  │         系统 B                  │
│  ┌──────────────────┐         │  │  ┌──────────────────┐         │
│  │ Blazor WASM 前端  │         │  │  │ Blazor WASM 前端  │         │
│  │ · 功能1           │         │  │  │ · 功能3           │         │
│  │ · 功能2           │         │  │  │ · 功能4           │         │
│  └────────┬─────────┘         │  │  └────────┬─────────┘         │
│           │ HTTP API          │  │           │ HTTP API          │
│           ▼                    │  │           ▼                    │
│  ┌──────────────────┐         │  │  ┌──────────────────┐         │

│  │ · 职责X           │         │  │  │ · 职责Y           │         │

### 10. AC 中使用模糊用语

**症状**：AC 中使用「正常」「相关」「主流」「合理」「良好」等不可测量的模糊词。

**对策**：
- AC 中的每一个可验证条件必须是二进制（通过/不通过）可测量的
- 发现模糊词时替换为具体描述：
  - 「正常运行」→「正常执行，无异常报错」
  - 「主流的现代浏览器」→「Google Chrome 和 Microsoft Edge 的最新版本」
  - 「相关的 .dll」→「甲方提供的 .dll」
  - 「合理的时间内」→给出具体阈值（5 秒、500ms 等）
- 编写完所有 AC 后，扫描全文检查模糊词残留

### 11. 遗漏异常/边界场景

**症状**：AC 只描述了正常路径（Happy Path），缺少异常处理。

**常见遗漏场景**：

| 领域 | 典型遗漏边界 |
|:----:|-------------|
| 文件导入 | 格式不支持、文件损坏、文件过大 |
| 参数配置 | 空配置时操作、参数值超出范围 |
| 文件生成 | 无内容时生成、同名覆盖策略 |
| 外部依赖 | 后端不可用、.dll 缺失或版本不匹配 |
| UI 交互 | 窗口缩放、数据量过大时性能下降 |

**对策**：
- 每条需求至少检查 1 个异常场景
- 多输入需求检查空值、越界、格式错误三条边界
- 多文件操作需求检查同名处理策略
- 外部依赖需求检查组件不可用时的行为

### 12. 需求条目包裹围栏后格式错乱

**症状**：批量给需求加 ``` 围栏后，出现连续两个 ``` 中间无内容的空围栏，或 ``` 与章节 `---` 分隔线冲突。

**对策**：
- 应当在编写每条需求时同步加围栏，尽量不要事后批量添加
- 如果必须批量添加，用 Python 脚本逐行处理，而不是 regex 替换
- 完成后用脚本验证：围栏数 = 需求数 × 2，不应出现连续两个 ``` 且中间无内容
- 围栏内不要包含章节分隔线（`---`）——分隔线应放在围栏外

### 13. 架构描述需要通过多轮修正才能精确

**症状**：用户纠正了架构描述（如"不是共享后端，是各自独立的后端"），意味着架构图、§1.6 系统关系、§6 系统交互需求全部需要联动调整。

**对策**：
- 架构描述不仅是 §1.5 架构图的事——§1.6 系统关系、各系统的 Description、§6 交互需求、甚至追迹矩阵都需要联动更新
- 当用户纠正一个架构点时，全文搜索所有相关描述（"共享""同一后端""同一存储""上传至后端"等关键词）以确保没有残留
- 架构图更新后，无法通过 cat 展现的"残留在旧架构图下方的分隔线"等细微格式问题需要用 `read_file` 完整重读一遍
- 如果 SRS 的内容是基于错误的架构假设写成的（如假设共享后端），需求条目本身（如 REQ-F-033~036）也需要重写以匹配真实架构

### 14. AC 独立为子需求时的引用替换完整性

**症状**：将 AC 提取为独立子需求后，仅删除了原 AC 但忘记在 Description 中补充引用，导致原需求与提取出的新需求之间的关联丢失。

**对策**：
- 原需求的 AC 位置应替换为引用（`参见 REQ-F-XXX`），而不是直接删除
- 原需求的 Description 末尾应补充说明：`xxx功能（参见 REQ-F-XXX）由独立需求定义`
- 追迹矩阵中为新增需求追加对应行
- 附录 B 统计表的章节区间和总数同步更新

### 16. TP §2 插件工具需求的细化深度不足

**症状**：直接将 TP §2 的 7 节内容各映射为一条简单需求（如 TP §2.3「菜单栏」→ 只有「菜单栏应包含 XX 操作」），遗漏了从 TP 原文中可以进一步派生的行为约束。

**TP §2 常见可细化点清单**（对 TP §2 逐句回归时可参考）：

| TP 条款 | 原文中的隐含行为 | 可细化的方向 |
|:-------:|:----------------|:-------------|
| §2.1 | 「开发 UA 的图层」 | 图层内 Widget 布局调整、排列、删除操作 |
| §2.1 | 「生成二进制 DF 和 XML DF」 | 二进制与 XML 的内容一致性约束、DF 格式标准引用 |
| §2.2 | 「编辑区」作为核心交互区域 | Widget 选中/取消选中高亮、编辑区基本交互行为 |
| §2.2 | 「结果输出区」在布局底部 | 结果输出区的功能定义（操作状态、进度、错误信息） |
| §2.3 | 「属性设置」下有具体属性项 | 属性设置对话框/面板（图层大小、图层 ID、DF UA ID） |
| §2.3 | 「剪切、复制、粘贴」 | 明确这些操作的作用对象（Widget 还是 Layer） |
| §2.3 | 「导入 DF 文件」同时在菜单和工程管理中出现 | 明确入口关系（不同入口调用同一功能） |
| §2.4 | 「管理工程文件和文件夹」 | 文件夹的创建、重命名、删除 |
| §2.5 | 「所有 widget 插件」 | 插件搜索/过滤（当 widget 数量较多时） |
| §2.6 | 「树状结构管理」 | 树内拖拽排序（同级顺序调整）、跨 Layer 拖拽移动 |
| §2.7 | 「所有参数」+「修改参数」 | 参数列表根据 Widget 类型动态变化、参数修改实时预览联动 |

**对策**：
- §2 的每个条款不应只映射为一条需求，应根据「开发」「管理」「编辑」等动词进一步拆分
- 界面布局条款不仅要列出功能区名称，还要定义每个功能区的基本交互行为
- 菜单栏条款不仅列出菜单项，还要定义每个操作的作用对象和触发方式
- 对每个功能区，至少检查是否有「操作 → 预览 → 修改」循环覆盖

**症状**：新增子需求的编号按顺序追加（REQ-F-044~048），但放置位置按业务归属（§4.5 和 §5），导致编号顺序与文档物理顺序不一致。

**对策**：这是可接受的做法——REQ-F 编号仅仅是标识符，不要求与文档物理顺序一一对应。编写时在 Description 中用"参见 REQ-F-xxx"维持关联即可。但要确保附录 B 统计表中的章节区间正确反映实际分布，不要假设区间连续。

### 17. 需求粒度过粗，AC 承载了多条独立功能点

**症状**：一条需求的多个 AC 描述了互不依赖的不同功能。例如「线型 .c/.h 生成」的 AC1="空配置校验"、AC2="生成 .c 文件"、AC3="生成 .h 文件"、AC4="编译兼容"，这些各自是独立的可测试点。

**粒度判断标准**：如果一个 AC 的 Given/When/Then 与其他 AC 完全不共享相同的前置条件和触发操作，且有独立的可判定结果，那么它应该是一条独立的需求。

**拆分原则（AC 原子化）**：
- 同一需求内的多个 AC，如果它们的 Given 条件不同、触发操作不同、验证结果不同，则应拆分为独立需求
- 共享相同 Given/When 的 AC（如「修改成功后界面更新」和「修改后数据持久化」）可保留为同一需求的多个 AC
- 保留准则：**「当用户执行一个操作，系统应检查 X、生成 Y、保存 Z」→ 这是三条需求。**「当用户输入无效值，系统应提示」→ 这是原需求的一条 AC，不应独立

**正向示例（可保留在同一需求的多个 AC）**：

```
REQ-F-00XX 色表值域校验
  AC1：R 值超出范围 → 提示
  AC2：G 值超出范围 → 提示
  AC3：B/A 值超出范围 → 提示
  → 合理：共享 Given（用户输入色表值）+ When（输入超范围值）+ Then（提示）
```

**反向示例（应拆分的 AC）**：

```
REQ-F-00XX 线型 .c/.h 文件生成（旧版 — 太粗）
  AC1：空配置校验 → Given(无条目) When(点击生成) Then(提示)
  AC2：.c 文件生成 → Given(有条目) When(点击生成) Then(.c 输出)
  AC3：.h 文件生成 → Given(.c 已生成) When(生成) Then(.h 输出)
  AC4：编译兼容 → Given(.c/.h 已生成) When(编译) Then(通过)
  → 问题：每个 AC 的 Given 和 When 完全不同，应拆为 4 条独立需求
```

## AC 独立为子需求（独立章节）

当用户主动询问「这些 AC 是否可以独立为一条子需求」时，执行以下流程：

### 适用条件

在标准的 TP→SRS 派生流程中，AC 不应随意独立。仅当用户**主动提出**时才做此操作。

### 评估标准

一个 AC 适合独立为子需求，当它同时满足以下条件：

| 条件 | 说明 |
|:----:|------|
| **独立操作用例** | AC 描述的是完整的用户操作场景，而非简单的输入校验 |
| **有独立的 Title** | AC 场景名称本身就是一个有意义的功能标题 |
| **偏离主需求核心范畴** | 主需求的 Title 无法概括该 AC 的内容 |

不应独立的情况：异常/校验场景（空配置校验、值域校验、无效文件处理等）应保留为原需求的 AC。

### 提取工作流

1. **评估**：遍历 AC，标记适合独立的候选，向用户确认
2. **分类**：正常路径的复杂操作（独立）vs 异常校验（保留为 AC）
3. **编号**：从当前最大 REQ-F 编号后递增
4. **放置**：按业务归属放到对应章节（编号顺序与文档物理顺序可以不匹配）
5. **替换**：
   - 原 AC 位置替换为 `参见 REQ-F-XXX`
   - Description 末尾补充引用
6. **更新附录**：追迹矩阵追加新行、统计表更新章节区间和总数、变更记录追加行
7. **验证**：围栏数 = 新总需求数 × 2，统计表与头部一致
