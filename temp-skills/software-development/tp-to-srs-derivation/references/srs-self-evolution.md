# SRS 文档自进化检查清单

当用户要求对 SRS 文档做自进化（文档质量检查）时，聚焦以下三个维度。本文件是 tp-to-srs-derivation 技能的 Phase 8/9 的参考。

## 维度一：术语一致性

检查全文使用的术语与 §1.3 术语表是否一致。

### 检查项

- [ ] 术语表中定义的术语，在正文中是否始终使用同一名称
- [ ] 中英文混用检查：同一概念在正文中是否有中英文交替的情况
- [ ] 优先 emoji（🔴🟡🟢）是否在所有需求头部使用，而非仅在 §1 的约定表中定义
- [ ] Actor 名称是否与 §1.4.3 定义的名称一致（不要出现同一角色两种写法）

### 典型问题

- `widget` vs `Widget` 大小写不一致
- `.dl1` vs `.dll` 等文件后缀笔误
- 同一术语在需求和描述中使用不同方案

## 维度二：AC 可测试性

检查每条验收条件是否明确、可测量、可二进制判定（通过/不通过）。

### 检查项

- [ ] 每条需求都有至少一个 AC
- [ ] 每个 AC 都有 Given/When/Then 三段
- [ ] AC 中没有模糊词：「正常」「合理」「良好」「适当」「足够」「相关」
- [ ] AC 的 Then 可以明确判定（通过/不通过），而非依赖主观判断

### 模糊词替换对照表

| 原文（模糊） | 修改（可测） |
|:------------:|:------------:|
| 正常运行 | 正常执行，无异常报错 |
| 相关的 .dll | 甲方提供的 .dll |
| 主流现代浏览器 | Google Chrome 和 Microsoft Edge 的最新版本 |
| 合理的时间内 | 应在 5 秒内 |
| 界面响应良好 | 界面应在 500ms 内给出视觉反馈 |
| 足够多的条目 | 应支持不少于 100 条 |

## 维度三：边界案例遗漏

检查每个需求是否遗漏了异常或边界场景。

### 通用检查模式

对于每条需求的每个 AC，问三个问题：

1. **Happy Path**：正常流程走了吗？（通常已有）
2. **Empty/Null Path**：如果是空的/没配置/没有输入怎么办？
3. **Error Path**：如果输入无效/文件损坏/外部依赖不可用怎么办？

### 按领域分类的常见遗漏

#### 文件导入类（图像/字体/.dll）
- 不支持的文件格式 → 应提示
- 文件损坏 → 应提示
- 文件过大 → 应有尺寸限制或提示
- 同名重复导入 → 处理策略（覆盖/重命名/跳过）

#### 参数配置类（线型/色表）
- 空配置时点击生成 → 应提示先配置
- 参数值越界（RGBA > 255 等）→ 应有输入校验
- 极端值（色表 0 条目 / 10000 条目）→ 边界处理

#### 文件生成类
- 生成时无任何内容 → 应提示用户
- 生成大量条目时的性能表现
- 文件名冲突处理

#### 外部依赖类
- 后端不可用 → 前端应展示提示
- .dll 缺失或版本不匹配 → 应有明确的错误信息
- 浏览器不支持 Blazor WASM → 应有降级提示

#### UI 交互类
- 浏览器窗口缩放 → 布局是否自适应
- 数据量过大（大量图元/大量 Widget）→ 是否有性能退化
- 连续快速操作 → 是否有防抖/节流

## 修正原则

### 优先级判定

| 类型 | 优先级 | 操作 |
|:----:|:------:|:----:|
| 核心功能缺失的边界 | 🔴 P0 | 补 AC |
| 用户体验优化的边界 | 🟡 P1 | 补 AC |
| 极端情况的设计决策 | 🟢 P2 或留到设计阶段 | 跳过或标记 |
| 模糊词替换 | 🟡 P1 | 修正为可测描述 |
| 缺少的交叉引用 | 🟡 P1 | 在 Description 中补充「参见 REQ-F-xxx」 |

### 补充 AC 而非新建需求

边界场景通常是对已有需求的自然延伸，在已有需求的 AC 列表中追加即可，不要创建新的 REQ-F 条目。

### 不过度偏离 TP

如果某个边界场景在 TP 中没有涉及且在协议上下文中不太可能发生，可以跳过。超出 TP 范围的内容应在标注「衍生：」后由用户确认。

## 多轮自进化工作流

当用户连续要求多轮自优化时，按以下分层递进：

### 第 1 轮：边界场景 + 模糊词

1. 读全文档
2. 扫描每个 AC 的模糊词（正常/相关/主流/合理/良好/适当/足够）
3. 扫描每个需求遗漏的边界场景（空配置/越界/文件损坏/后端不可用）
4. 输出修改清单 → 用户确认 → 修正
5. 验证统计一致性，更新变更记录

### 第 2 轮：交叉引用 + 粒度

1. 识别有上下游依赖关系的需求对（配置→生成、绘制→保存）
2. 为上游需求的 Description 补充向下游的引用（参见 REQ-F-xxx）
3. 识别仅有 1 个 AC 的需求，判断是否可以补充更多场景
4. 优先补充在 TP 中有明确依据的新 AC
5. 输出修改清单 → 用户确认 → 修正
6. 验证统计一致性，更新变更记录

### 第 3 轮：TP 逐句回归

1. 重读 TP.md 原文，逐句标记每个条款
2. 与 SRS 需求逐条对照，确认已覆盖
3. 识别首次遗漏的可派生点（TP 中有但 SRS 未反映的约束/行为）
4. 检查架构描述是否与实际设计方案一致（如需修正则联动修改架构图、系统关系描述、交互需求）
5. 如果是**精确性修正**（如可编辑文件同步时序从「生成后」改为「过程中」），修改 AC 的 Given/When 描述而不改变需求框架
6. 输出修改清单 → 用户确认 → 修正
7. 验证统计一致性，更新变更记录

### 第 4 轮：AC 粒度审查（可选，仅当用户主动提出）

如果用户问「这些 AC 是否可以独立为子需求」，执行以下操作：

1. 遍历所有 AC，按以下标准分类：
   - **独立操作用例候选**：描述完整用户操作场景，有独立 Title，偏离主需求核心范畴
   - **保留为 AC**：异常/校验场景（空配置校验、值域校验、无效文件处理等）
2. 输出候选清单给用户确认
3. 确认后按 **AC 独立提取工作流**执行：编号递增 → 按业务归属放置 → 原位置替换为引用 → 更新 Description → 更新附录
4. 验证围栏数、统计一致性

### 收敛判断

- 第 3 轮改动量 < 总行数 5% → ✅ 收敛，停止
- 第 3 轮改动量 >= 5% → 仅对第 3 轮发现做第 4 轮聚焦修正
- 第 4 轮改动量仍 >= 5% → 停止并标注为「需人工审阅的争议项」

## 常见遗漏派生点模式清单

在 TP 逐句回归轮次中，以下模式最容易在首次编写时遗漏：

| 模式 | TP 原文信号词 | 典型遗漏 |
|:----:|:-------------|:---------|
| **标准约束** | 「根据 A661 标准要求格式」 | 只写了输出格式，未显式引用 A661 标准约束 |
| **过程描述** | 「在生成的过程中同步」 | AC 写成了生成后同步（事后），应改为过程中同步（实时） |
| **组合属性** | 「属性的组合」 | 只覆盖了单个属性，忽略了属性之间的关系 |
| **开发流程** | 「开发」「构建」 | 只覆盖了单步操作（放置），忽略了完整工作流（选择→调整→组合→保存→导入） |
| **文件夹管理** | 「管理工程文件和文件夹」 | 只覆盖了文件操作，遗漏了文件夹管理（创建/重命名/删除） |
| **输出反馈** | 「结果输出区」 | 只画了布局图，未描述该区域的功能行为 |
| **解析入口** | 「可解析符号」 | 只覆盖了从零新建，遗漏了导入已有文件进行编辑的场景 |
| **可编辑文件时序** | 「过程中同步」 | 写为「生成.c/.h的同时也生成可编辑文件」，实际应表述为：用户在配置过程中系统即后台维护可编辑文件状态，完成时与输出文件一并导出 |
| **线型类型** | 「可配置线的线型」 | 只覆盖了占空比/线宽/颜色组合，遗漏了线型类型选择（实线/虚线/点划线） |
